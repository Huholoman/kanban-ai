# kanban-ai — specification

Status: prototype. This document describes what the tool does today (commit after `7b2b06f`); `README.md` is the quick tour, this is the reference.

## 1. Purpose and model

kanban-ai is a backlog for several coding agents (and humans) working in parallel, typically one agent per git worktree. The backlog is a plain folder of Markdown files with YAML front matter, so it can be versioned in git, edited by hand and read by any tool. On top of it there are:

- **`backlog`** — a CLI for agents and people (all commands have `--json`),
- **`backlog-server`** — a REST + WebSocket API that also serves the web board,
- **the web board** — a Flutter web app (kanban, lists, dependency tree, editable detail).

Everything derived (ready, blocked, progress, …) is computed from the files on every read; there is no database and no cache to get out of sync.

```
<project>/
  backlog/                ← the backlog (often its own git repo)
    backlog.yaml          ← workflow configuration
    items/<id>-<slug>.md  ← one file per item
    views/<id>.yaml       ← saved views
    docs/                 ← longer documents items can link to
    .locks/               ← claim locks (machine-local, git-ignored)
  monorepo/, monorepo-2/, …  ← worktrees; the CLI finds ../backlog from any of them
```

### 1.1 Locating the backlog

In this order: `-C/--dir`, `$BACKLOG_DIR`, then from the current folder upwards the first folder that contains `backlog.yaml` or has a `backlog/` subfolder containing it. The second rule lets every sibling worktree find a shared `../backlog`. `backlog-server` prefers the project registry (§1.2) to the last rule, see §8.

### 1.2 Project registry

One machine usually has several backlogs (one per project). The registry lists them for `backlog-server` (§8), which hosts all of them at once and picks up edits of the file live. It is a YAML file, by default `$XDG_CONFIG_HOME/kanban-ai/projects.yaml` (`~/.config/kanban-ai/projects.yaml` without `XDG_CONFIG_HOME`), elsewhere with `$BACKLOG_PROJECTS` or `--projects <file>`:

```yaml
projects:
  - id: kanban-ai                  # optional: slug of the project folder
    name: kanban-ai                # optional: the project folder's name
    path: ~/p/kanban-ai/backlog    # absolute, ~/… or relative to this file
  - path: ~/p/hobbyo/backlog       # → id hobbyo
```

- **Project folder** is the backlog folder itself, or its parent when the folder is called `backlog` (`~/p/hobbyo/backlog` → `hobbyo`).
- **id** — lower-case letters, digits, `-`, `_`, starting with a letter or digit; unique within the registry (a repeated or invalid id makes the whole file invalid). It appears in URLs (`/api/p/<id>/…`).
- **Order** matters: the first project is the *default project*.
- **pinned** — optional `true`/`false` (default false), read and written back; the board's project switcher offers pinned projects first (§9). Set with `backlog projects pin|unpin <id>` or `PATCH /api/projects/<id>`; unpinning removes the key.
- Unknown keys and comments are kept; `backlog init`, `backlog projects add/remove` and `backlog config` (Global › Projects, §5) edit the file in place. A missing file is an empty registry.

## 2. Configuration — `backlog.yaml`

```yaml
id:
  prefix: X        # ids look like X-7f3a
  length: 4        # random part from 23456789abcdefghjkmnpqrstuvwxyz; random so that parallel agents never clash

statuses:          # board order
  - id: backlog
    category: open           # open | active | done
  - id: todo
    category: open
    pickable: true           # agents may take items in this status as ready work
  - id: in-progress
    category: active
  - id: review
    category: active
  - id: done
    category: done
  - id: cancelled
    category: done

priorities: [p0, p1, p2, p3]           # most urgent first
types: [task, story, epic, bug, decision, idea]
milestones: []                         # empty = any name allowed
#  - id: launch
#    title: Production launch
#    due: 2026-12-01

defaults:
  status: backlog
  priority: p2
  type: task

claims:
  lease_minutes: 240                   # a claim without heartbeat expires after this

git:                                   # optional; how the server keeps the backlog's own repository (§8 *Committing the backlog*)
  commit: auto                         # auto (default: the server commits it when it is the top of its own repository) | off
  push: false                          # push after each commit (default false)

appearance:                            # optional; colours "#rrggbb" (quoted!), "#rgb" or without "#"
  mode: system                         # system | light | dark
  light: {seed: "#3f51b5"}             # also primary, secondary, background
  dark: {seed: "#8c9eff"}
  statuses: {todo: "#1e88e5"}
  priorities: {p0: "#e53935"}
  types: {epic: "#6a1b9a"}
  labels: {infra: "#00897b"}

dispatcher:                            # optional; without it there is no dispatcher
  mode: manual                         # manual (propose new work, a person starts; replies still wake agents) | auto (start by itself)
  max_agents: 2                        # at most this many at once; default one per worktree
  worktrees:                           # in order of preference
    - name: monorepo-2                 # also the agent name of its claims
      path: ../monorepo-2              # absolute, or relative to the backlog folder
    - monorepo-3                       # bare name = {name: monorepo-3, path: ../monorepo-3}
  repo: ../monorepo                    # optional: add worktrees from this primary clone when none is free (§8.2)
  worktree_name: "{repo}-{n}"          # name of added worktrees (default); next to repo, first unused n from 2
  max_worktrees: 4                     # listed + added (with repo; default max_agents)
  cleanup_after_days: 14               # remove added ones idle this long when nothing is lost (default: keep)
  setup: [[mise, trust], [mise, run, get]]   # prepare an added worktree before an agent starts there (with repo)
  base: main                           # new branches agent/<id> start from here (default main)
  agent: claude                        # agent profile (default claude): built-in or from agents
  agents:                              # optional own profiles (may replace a built-in one)
    my-claude:
      command: claude -p {prompt} --model sonnet   # string (split like a shell) or list of arguments
      env: {MY_VAR: "{worktree}"}      # extra environment, placeholders allowed
      output: claude-stream-json       # text (default) | claude-stream-json | json-lines
      resume: --resume {session}       # optional: arguments appended to continue a session
  prompt: |                            # optional; shared by all profiles, fills {prompt}
    Work on backlog item {id}, run backlog show {id} first.
  resume_prompt: |                     # optional; the prompt when an agent continues its session
    Continue on {id}. Since your last run: {news}
  actions:                             # optional: buttons on items and status hooks (§8.2)
    - name: Fix PR comments            # unique; the button's label, the name in the API and CLI
      statuses: [review]               # items in these statuses show the button (default below)
      prompt: "Go through the unresolved comments of PR {pr}, fix them, push and answer them."
      changes_code: true               # its agent changes code: the item shows in-progress while it runs (§8.2)
      # agent: claude                  # profile (default: agent above)
      # fresh: false                   # true: a new session instead of the item's own
    - name: AI review
      on_enter: review                 # runs by itself, once, when an item enters review
      review: true                     # an AI review: built-in task, new session, ends with backlog review
      # prompt: "Also check the migrations."   # with review: added to the built-in task
      # auto_fix: 2                    # with review: on changes the item's agent fixes them, at most 2 rounds
      # then: review                   # with review in a status of its own (on_enter: ai-review): go on to review (§8.2)
    - name: Merge
      on_enter: deploy
      run: merge                       # a built-in action by name (noop, merge, preview)
    - name: Deploy locally
      statuses: [review]
      run: preview                     # the board runs from the item's branch rebased onto base (§8.2)
    - name: Tests
      statuses: [review]
      run: [sh, -c, "mise run check"]  # a command: a list of arguments, placeholders allowed
  pr:                                  # optional; agents push their branch and open a pull request (§5 `pr`)
    remote: origin                     # default origin
    create: 'tea pulls create --head {branch} --base {base} --title "{id}: {title}" --description-file -'
    find: 'gh pr list --head {branch} --json url --jq ".[0].url"'   # optional: URL of an open PR of the branch
    url_pattern: 'https://\S+/pulls/\d+'   # optional; group 1 or the match is the URL (default: first http(s) URL)
    review: 'tea comment {pr_number}'  # optional: backlog review posts the review to the pull request (body on stdin)
    # review: 'gh pr review {pr} --comment --body-file -'
    merge: tea pulls merge --style rebase {pr_number}   # optional: how `run: merge` merges the PR (gh: gh pr merge --rebase {pr})
    state: gh pr view {pr} --json state --jq .state      # optional: merged | closed | open; notices PRs merged elsewhere (§8.2)
    state_every: 2                     # minutes between two state checks of an item (default 2)
  merge:                               # optional; the built-in action merge (§8.2)
    strategy: local                    # pr (default with pr) | local (default without) | command
    check: mise run check              # local: run after the rebase; a failure stops the merge
    push: false                        # local: push the merged base to remote
    remote: origin                     # default pr.remote, else origin
    # command: [./ship.sh, "{branch}"] # strategy command: merges by itself, exit code 0 = merged
    cleanup: true                      # afterwards remove the branch, a created worktree and the session (default)
  preview:                             # optional; the built-in action preview (§8.2)
    worktree: "{repo}-preview"         # helper worktree next to the primary clone (default)
    check: [sh, -c, "mise run get && mise run check"]   # optional: run after the rebase; a failure stops it
    install: [mise, run, install-dev]  # optional: builds and installs the preview
    server: backlog-server-dev         # optional: the server restarts as this program (default: no restart)
    main_server: backlog-server        # optional: what "Back to main" restarts it as (default: the program it runs as)
  # legacy: command: claude -p "Work on {id}"  (instead of agent; a plain profile, output text)
```

Semantics:

- **Status categories** drive behaviour: `open` = not started, `active` = being worked on, `done` = finished (any done-category status, e.g. `cancelled`, counts as finished for dependencies).
- **Pickable status** — the open status agents take work from (`todo`). `claim` moves an item to the first `active` status; `release` returns an active item to the pickable status.
- **Priorities** are ordered; the first is the most urgent. They rank items inside a milestone: ready work goes by milestone first (§3.1).
- **Milestones** play the role of versions/releases; when the list is non-empty, `lint` warns about unknown ones.
- **Types** are labels; the hierarchy comes from `parent`, not from the type. `epic` is special only in the UI (epic filter, the default Board view hides epics).
- **Statuses are the board columns.** Add, rename or reorder them here; each view chooses which to show with `columns:` (§6), also editable from the app.
- **Appearance** only affects the web board: the palette is generated from `seed` per brightness, `primary`/`secondary`/`background` override parts of it; status, priority, type and label colours replace the built-in ones (columns, card stripes, tags). Invalid colours or modes are configuration errors.
- **Dispatcher** hands ready items to agents running in the listed worktrees. A worktree is *free* when no live claim is held under its name; at most `max_agents` of the listed worktrees are busy at once. **Agent profiles:** `agent` names the profile to start (default `claude`); built in are `claude` (`claude -p {prompt} --output-format stream-json --verbose --permission-mode acceptEdits --permission-prompts none --allowedTools "Bash(backlog *) Bash(git *) Bash(mise *) Bash(dart *) Bash(flutter *) Bash(./*) Bash(ls *) Bash(cat *) Bash(head *) Bash(tail *) Bash(wc *) Bash(find *) Bash(grep *) Bash(rg *) Bash(jq *) Bash(diff *) Bash(sort *) Read Edit Write Grep Glob TodoWrite WebFetch WebSearch" --disallowedTools "Bash(git push *) Bash(git -*) Bash(git send-pack *) Bash(git config *alias*)"`, output `claude-stream-json`, resume `--resume {session}`; verified with Claude Code 2.1, runs on the subscription login — never `--bare`, never `--dangerously-skip-permissions`; the deny list also covers pushes behind git's global options such as `git -C . push`, which `Bash(git push *)` alone lets through, `git send-pack` and aliases) and the unverified presets `codex` (`codex exec --full-auto --json {prompt}`, `json-lines`), `gemini` (`gemini --approval-mode auto_edit -p {prompt}`) and `aider` (`aider --yes-always --message {prompt}`). **Tool rules:** `allow` and `deny` (lists of Claude Code permission rules, e.g. `allow: ["Bash(dotnet *)"]`) are added to the `--allowedTools` and `--disallowedTools` lists of the built-in `claude` profile and of every own profile whose command has an `--allowedTools` (`--allowed-tools`) argument (a missing `--disallowedTools` is then appended); other profiles are unchanged, and `lint` warns (`dispatcher-allow`) when the agent or the agent of a prompt action is such a profile while `allow`/`deny` is set. The built-in push ban always stays. `agents: {name: {command, env, output, resume}}` defines more profiles or replaces built-in ones (`command` required; `env` a map of variable → value; `output` `text` | `claude-stream-json` | `json-lines`, default `text`; `resume` the arguments appended to the command to continue an earlier session, `{session}` being its id — only used with `claude-stream-json`, the one output a session id is read from, §8.2). **Resume prompt:** `resume_prompt` replaces `prompt` when an agent continues its session on the item; it has the prompt's placeholders and `{news}` (how the last run ended — `your last run exited with code 1; it left in-progress, released and held.` — and either `No new comments in the discussion.` or the new comments of others, each with its heading line); the default says that the agent continues item {id} on {branch}, gives `{news}`, asks it to look at the item again, then: when the comments only ask something, to answer with `backlog comment` and stop without changing code or status (an item it had handed over goes back to `{handover}` by itself, §8.2 *Who has the ball*); when they answer its question or ask for changes, to reply briefly and go on under the same rules, finishing with `backlog set {id} status={handover}` unless the comments name another status (e.g. to merge again after a failed merge); to update the description or acceptance criteria above `## Discussion` (`backlog describe`, as below) when the discussion changed the assignment; and to ask again with `backlog ask` when still unclear. **Prompt:** `prompt` is one template shared by all profiles; the default tells the agent its name ({worktree}) and item, to run `backlog instructions` and `backlog show {id}` first, to read the comments in the item's `## Discussion` before starting and take them into account — when one asks it something or raises a point it cannot settle alone, to answer it with `backlog ask {id} "…"` (handing the item to a person) and stop before changing anything —, to commit on the prepared branch `{branch}` in small commits containing the id, to finish with `backlog set {id} status={handover}`, never to push, to ask with `backlog ask {id} "…"` and stop when something is unclear, and to update the description or acceptance criteria above `## Discussion` when a discussion changes the assignment — with `backlog describe {id} --file .kanban-ai/item-{id}.md` (optionally `--section "Acceptance criteria"`), never by editing the item file, which lies outside the worktree. Every default prompt (and the frames of prompt actions and fix rounds) adds three rules: **checklist** — tick off finished checklist items with `backlog check {id} <number or text>` (§5), never by editing the item file (it lies outside the agent's worktree, so the edit would need an approval nobody can give); **talking** — the discussion is for questions, answers and problems only: comment only to ask (`backlog ask`), to answer a person's question, or once when something failed or could not be finished (a push or pull request failed, checks do not pass, a permission was denied, a tool is missing: what happened and what is needed; `backlog ask` when a person has to decide), never to acknowledge an answer, report progress or summarise work that went well (that belongs in commits and the pull request description), in the language the people in the item use; **running** — project scripts directly as `./script args` (not `sh script`), one command per call without `;`/`&&` chains, the Read, Grep and Glob tools preferred for files; besides backlog, git, mise, dart, flutter, common read-only commands and web search/fetch only what the project allows runs, since anything outside the tool whitelist needs an approval nobody can give; every command on one line — a long or multi-line text is written with the Write tool to a file in `.kanban-ai/` and passed with `--file` (`backlog comment/ask/review`). The backlog is the board's to commit (§8 *Committing the backlog*): never commit it, never report its uncommitted changes as a problem, look at it with `backlog` (never with git), and run git only in the worktree, without `-C <dir>` (denied). The launcher adds `/.kanban-ai/` to the repository's shared `info/exclude` when it creates a worktree and before an agent starts (once; never committed), so these files leave the worktree clean; the check whether a worktree is clean (free, may be detached) skips the folder anyway, even where git does not ignore it. With `pr` set, the default `prompt` replaces "never push" by: finish by writing a pull request description (what and why, how it was verified, that it implements {id}) to `.kanban-ai/pr-{id}.md` and running `backlog pr {id} --description-file .kanban-ai/pr-{id}.md`, then `backlog set {id} status={handover}`; never run `git push`, push other branches or merge — `backlog pr` is the only way out (when it fails, say so with `backlog comment` and still set review); the default `resume_prompt` likewise says to finish with `backlog pr {id}` (it pushes; a description only when there is no pull request yet). **Pull requests:** `pr.create` (required) and `pr.find` are commands like the agent's (string or list, no shell) with the placeholders `{id}`, `{title}`, `{branch}`, `{base}`, `{remote}`, `{description}`; `pr.review` (optional) is a command too, run by `backlog review` (§5) to post a review to the item's pull request, with `{id}`, `{title}`, `{branch}`, `{base}`, `{remote}`, `{pr}` (the item's `pr`), `{pr_number}` (its number, as for `pr.merge` below), `{verdict}` (`ok` \| `changes`) and `{body}` (the text posted, also on its standard input); `remote` must not start with `-` or contain spaces; `url_pattern` is a regular expression (its first group, else the whole match, is the URL; terminal colour codes are removed first). Without `pr` nothing pushes or opens pull requests. The legacy `command` (instead of `agent`) is a plain profile with output `text`. Commands are split into arguments like a shell would (quotes, backslashes) but never run through one, so pipes or variables need an explicit `[sh, -c, "…"]`; `{id}`, `{title}`, `{worktree}`, `{path}` (absolute worktree path), `{backlog}` (absolute backlog path), `{branch}` (the branch prepared for the agent, §8.2) and `{handover}` (the status the agent hands its work over in: the status the item had when it started if that is an `active` one after the first, else the `on_enter` status of an AI review with `then` — e.g. `ai-review` —, else `review`, §8.2 *Who has the ball*) are replaced in the prompt, every command argument and `env` value, `{prompt}` (the rendered prompt) in commands and `env`; `{{`/`}}` are literal braces. The agent runs inside the worktree folder with `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=true` (git never waits for an editor nobody sees, e.g. in `git rebase --continue`), `BACKLOG_AGENT=<worktree>`, `BACKLOG_DIR=<backlog>` and the profile's `env` (which may replace any of them) added to the server's environment. **Worktrees on demand:** with `repo` (the primary clone, absolute or relative to the backlog folder) the dispatcher also creates worktrees by itself when none is free, up to `max_worktrees` in all (listed plus created; defaults to `max_agents`, which then defaults to `max_worktrees`); `worktree_name` (placeholders `{repo}` = folder name of the clone, `{n}` required) names them, `cleanup_after_days` lets it remove idle ones, `setup` (a list of commands, each a list or one string split like a shell; placeholders `{worktree}`, `{path}`, `{repo}`, `{base}`) prepares each new one (§8.2). `worktrees` may then be left out. Unknown keys and placeholders, both `agent` and `command`, `allow` or `deny` that is not a list of non-empty strings, an unknown `agent`, a profile without `command`, an unknown `output`, invalid variable names, missing `worktrees` (without `repo`), `repo` without a limit, `worktree_name`, `max_worktrees`, `cleanup_after_days` or `setup` without `repo`, a `worktree_name` without `{n}` or giving an invalid name, `max_worktrees` below the number of listed worktrees, `cleanup_after_days` < 1, duplicate names or paths, names other than `[A-Za-z0-9._-]`, a `base` starting with `-`, `max_agents` < 1 and a `mode` other than `auto`/`manual` are configuration errors; `lint` warns about worktree paths that are not folders (`dispatcher-worktree`), a `repo` that is not a folder (`dispatcher-repo`), an agent program not on the `PATH` and unverified presets (`dispatcher-agent`), and a `pr.create`/`pr.find`/`pr.review` program not on the `PATH` (`dispatcher-pr`); unknown keys of `pr`, a missing `create`, unknown placeholders, an invalid `remote` or `url_pattern`, a `state_every` below 1 are configuration errors. `pr.merge` and `pr.state` have the placeholders `{id}`, `{title}`, `{branch}`, `{base}`, `{remote}`, `{pr}` (the item's `pr` URL) and `{pr_number}` (the number at its end: `…/pulls/7`, `…/pull/7/`, `…/merge_requests/7`, `#7`, `7`). **Merging** (`dispatcher.merge`, used by the built-in action `merge`, §8.2): `strategy` is `pr` (merge the pull request with `pr.merge`), `local` (rebase, `check`, fast-forward, optionally `push`) or `command` (an own `command`); the default is `pr` when `dispatcher.pr` is set, else `local`. `check` and `command` are commands like the others with the placeholders `{id}`, `{title}`, `{branch}`, `{base}`, `{remote}`, `{pr}`, `{pr_number}`, `{worktree}`, `{path}`, `{backlog}`; `remote` defaults to `pr.remote`, else `origin`; `cleanup` (default `true`) removes the item's branch, the worktree the dispatcher created for it and its agent session after a merge. Configuration errors: unknown keys, an unknown `strategy`, `command` without strategy `command` (and the other way round), `check` or `push` with another strategy than `local`, a non-boolean `push`/`cleanup`, an invalid `remote`, and — when a `run: merge` action or the `merge` section exists — strategy `pr` without `pr.merge`. `lint` warns (`dispatcher-pr`, `dispatcher-merge`) when a program of `pr.merge`, `pr.state`, `merge.check` or `merge.command` is not on the `PATH`. The running server plans with it and starts the agents (§8.2).
- **Actions** (`dispatcher.actions`, optional list): each has a `name` (unique, not empty, no `/`), exactly one of `prompt` (an agent: optional `agent` profile, default `dispatcher.agent`, `fresh: true` for a new session instead of the item's own, and `changes_code: true` when its agent changes code, so that the item shows in the first active status while it runs, §8.2 *Who has the ball*), `review: true` (an **AI review**: a prompt action with the built-in review task, always `fresh`; a `prompt` given with it is added to the task as `Also: …`; `auto_fix: N` lets the dispatcher wake the item's agent to fix the findings and review again, at most N rounds, default 0, §8.2; `then: <status>` with `on_enter` of a status of its own moves the item on to that status when the review is over, §8.2 *AI review in a status of its own*) and `run` (a list of arguments is a command; a single name is a built-in action: `noop`, which does nothing, or `merge`, §8.2), optionally `on_enter: <status>` (a hook: it runs by itself whenever an item enters that status) and `statuses` (the statuses whose items show it as a button; default every status, or only the `on_enter` status when that is set; `[]` makes a pure hook). Placeholders: a `prompt` has those of `dispatcher.prompt` plus `{pr}`, `{status}`, `{base}`, `{action}` and `{news}` (as in `resume_prompt`, or `This is a new session.`); a command has `{id}`, `{title}`, `{branch}`, `{pr}`, `{status}`, `{worktree}` (empty in the primary clone), `{path}` (where it runs), `{backlog}`, `{base}` and `{action}`. Configuration errors: unknown keys and placeholders, a missing or duplicate name, both or neither of `prompt` and `run` (without `review`), `run` with `review`, `fresh: false` with `review`, a `review` that is not a boolean, `auto_fix` without `review`, not a number or below 0, `then` without `review`, without `on_enter`, equal to it or an unknown status, an unknown built-in (`run: "make test"` is refused: commands are lists), unknown statuses in `on_enter`/`statuses`, an unknown `agent`, `agent`/`fresh` on a non-prompt action, a `fresh` that is not a boolean, `changes_code` on a non-prompt action or a review, or not a boolean. `lint` warns (`dispatcher-action`) about an action's program not on the `PATH`, an unverified preset as its agent and an action that can never run (no `on_enter`, `statuses: []`). How they run: §8.2.
- Changes to `backlog.yaml` are picked up by a running server (and the board's theme) without restart.

### 2.1 Presets — `backlog init --preset`

A preset is what `init` writes: a `backlog.yaml` template, views and optionally a guide for agents (Markdown for the repository's `CLAUDE.md` / `AGENTS.md`: `backlog instructions` at the start, `BACKLOG_AGENT` = the worktree, status and relations only through the CLI, checklists with `backlog check`, versions as milestones, the item id in every commit, `backlog lint` before the end). Built in:

| Preset | What it sets up |
|---|---|
| `default` | the commented template of §2 and the default views (`board`, `ready`, `hot`, `blocked`, `dependencies`) — what `init` writes without `--preset` |
| `minimal` | a personal to-do list: statuses `todo` / `in-progress` / `done`, priorities `p1`–`p3`, types `task`, `bug`, `idea`, no milestones, no dispatcher; views `board`, `open` |
| `agents` | coding agents as in kanban-ai itself: the statuses of `default` with `review`, milestones `v0.1` and `later` (versions as milestones, `later` the pile), a `manual` dispatcher creating its own worktrees next to the repository (`repo: ${repo}`, `worktree_name: "${repo_name}-agent-{n}"`, `max_worktrees: 2`, `base: main`, agent `claude`); the default views plus `epics` and a `v0.1` board in the section *Milestones*; the guide for agents |
| `agents-review` | `agents` plus the actions *AI review* (`review: true`, `on_enter: review`) and *Merge* (`run: merge` in `review`) with `merge.strategy: local`, `push: false` (the `check` is left for the project to fill in) |

**User presets** are folders in `$XDG_CONFIG_HOME/kanban-ai/presets/<name>/` (`~/.config/kanban-ai/presets/` without `XDG_CONFIG_HOME`); one named like a built-in preset replaces it. `--preset` also takes a folder: a value with `/`, or starting with `.` or `~`, relative to the current folder. A preset folder holds `backlog.yaml` (required), `views/*.yaml` (without the folder: the default views), `AGENTS.md` (the guide, optional) and `preset.yaml` (optional, `description: …` for the list).

**Placeholders** in the templates: `${prefix}` (the id prefix), `${project}` (the project folder's name, §1.2), `${repo}` (the code repository relative to the backlog folder, `--repo`, default `..`) and `${repo_name}` (its folder name); unknown `${…}` and the dispatcher's own `{…}` placeholders stay as they are.

**`--from <backlog>`** copies the `backlog.yaml` (comments included) and the views of an existing backlog (its folder, or found from it as in §1.1), not its items, discussions or claims; no placeholders are filled, paths in its `dispatcher` section are copied as they are. With `--prefix` the copy gets that id prefix (the rest of the file stays as it was).

## 3. Items — `items/<id>-<slug>.md`

```markdown
---
id: X-7f3a               # required, immutable
title: Production DB backups   # required, non-empty
type: task
status: todo
priority: p0
rank: 1024               # manual order where a view sorts by rank (§6)
milestone: launch
parent: X-m4an           # epic/story it belongs to
depends_on: [X-2c91]     # hard prerequisites — they block
related: [X-a004]        # context only, never blocks
assignee: monorepo-2     # set by claims
branch: feat/backups
pr: https://github.com/org/repo/pull/42
labels: [infra, db]
docs: [backups]          # names of files in docs/
touches: [deploy/backup/, "scripts/*.sh"]   # paths/globs in the code repository the work changes (§3.2)
created: 2026-10-29T08:12:00Z   # UTC; older files: a day (2026-10-29)
updated: 2026-10-29T14:05:31Z
estimate: 3d             # any unknown key is kept and can be filtered on
---

## Context
...
- [x] pick a tool
- [ ] tested restore     ← checklist progress is computed from these
```

Rules:

- **Ids** are `<prefix>-<random>`. Anywhere an id is expected, an unambiguous shortening works (`7f3a`, `X-7f`); an ambiguous one is an error listing the candidates.
- **File name** is `<id>-<slug-of-title>.md`; the slug strips diacritics (`Zürich DB backups` → `zurich-db-backups`). `lint` reports files whose name does not match.
- **Writing preserves the file:** comments, key order and unknown keys are kept, only changed keys are rewritten (YAML editing, not re-serialisation), so git diffs stay minimal. Writes are atomic (temp file + rename).
- **Rank** is a number (integer or decimal, may be negative) giving a manual order: a view with `sort: [rank, …]` lists lower ranks first and items without a rank after all ranked ones, in the order of its further sort keys. The board sets it when a card is dragged within a column; `set <id> rank=1024` sets it by hand, `rank=` removes it. A value that is not a finite number makes the file unreadable (`unreadable`), like any other malformed field.
- **Body** is free Markdown. Checkboxes `- [ ]` / `- [x]` give the checklist progress.
- **Discussion** is the section from a `## Discussion` heading (outside code fences) to the next level-1 or level-2 heading or the end of the body. Each comment starts with a heading line `### <author> · <YYYY-MM-DD HH:MM:SS> UTC` (seconds and ` UTC` optional when written by hand), followed by ` · question` for a question, ` · note` for a note (a comment that neither answers a question nor wakes the item's agent, §8.2) or ` · review ok` / ` · review changes` for a **review** (the verdict of a review of the item's work, `backlog review`; optionally followed by ` @<commit>`, 4–40 hex digits, the commit reviewed — the head of the item's branch then; like a note it answers no question and is no reply that wakes the agent, but a resumed agent sees it in `{news}`, even when the reviewer ran under the agent's worktree name; its *findings* are the lines of its text starting a numbered list, `1. …` or `1) …`, indented at most three spaces, outside code fences; headings without a marker are plain comments, as before); its text runs to the next comment heading (text before the first one is ignored; fences are never structure). `backlog comment` / `ask` (and `POST /api/items/<ref>/comments`) append a comment at the end of the section, or a new section at the end of the body, with a blank line around; headings of level 1–3 in the text become level 4, everything else in the body stays byte for byte. Authors lose line breaks, `·` becomes `-`; empty text or author is refused. Example:

  ```markdown
  ## Discussion

  ### monorepo-2 · 2026-10-31 14:05:12 UTC · question

  CSV or JSON for the export?

  ### tobik · 2026-10-31 14:20:03 UTC

  CSV.

  ### monorepo-3 · 2026-10-31 16:10:00 UTC · review changes @1a2b3c4d5e6f

  Works, two findings:

  1. lib/export.dart:40 – the header row is missing.
  2. No test for an empty backlog.
  ```
- **Times:** `created` (set when the tool creates the item) and `updated` (set on every change made through the tool that changes something) are UTC instants to the second, `2026-10-29T14:05:31Z`. Older files with only a day (`2026-10-29`) are still read (as midnight UTC) and keep their value until the tool changes that key; a hand-written time with an offset or without a zone (taken as UTC) works too. Sorting by them (the default order, `sort: created`) is chronological. The CLI text output shows them in the system's time zone (`show`), JSON as written plus `created_at`/`updated_at` (ISO 8601 in UTC, null for a day only); the board shows them, like the times of comments, in the browser's zone, relative to now for recent ones (`5 min ago`, `yesterday`, up to a week) with the exact time in a tooltip; they count on by themselves (one shared minute tick for the whole app, running only while a time is shown).

### 3.1 Derived state (computed, never stored)

| Field | Meaning |
|---|---|
| `category` | category of the status (`open`/`active`/`done`), null for an unknown status |
| `blocked` | not done, and some `depends_on` item is not done or does not exist |
| `blocked_by` | those unfinished/missing dependencies |
| `conflicting` | open (not started), has `touches`, and they overlap the `touches` or `changed_files` of an item in an `active` status (§3.2) |
| `conflicts_with` | those active items — the item waits for them ("waits for X") |
| `changed_files` | for an item in an `active` status: the files its branch (`branch`, else `agent/<id>`) changed since it forked from the base branch (§3.2); empty for other items |
| `needs_human` | not done, and the discussion has an open question: a `question` comment with no later comment by another author (notes do not count) |
| `review` | where the review of the item's work stands, from its latest review comment (§3): `none` (no review), `ok`, `changes`, or `stale` when the head of the item's branch (`branch`, else `agent/<id>`) has commits the review did not see — it is not the commit the review names, or, when it names none, it was committed after the review was written. Branch heads come from `git for-each-ref` in `dispatcher.repo`, else the first existing dispatcher worktree, else the backlog folder; with no repository or branch there a review never becomes `stale`. A running dispatcher also knows `running` (§8.2) |
| `review_findings` | the findings of the latest review when it asks for changes (its numbered list items, §3), else 0 |
| `ready` | in the pickable status, not blocked, not conflicting, not `needs_human`, no open children, and no live claim (expired claims do not count) |
| `children` | `{total, open}` — items whose `parent` is this one |
| `progress` | checklist `{done, total}` from the body |
| `claim` | current claim with `expired` flag |
| `has_children`, `claimed`, `claimed_by` | for views and filters |

Default order ("most urgent first"): priority, then `created`, then id.

Ready work (`ready`, `backlog next`, the dispatcher's order, §8.2) goes by milestone first: in the order of `milestones` in `backlog.yaml` (earlier versions first); items without a milestone, with `later` (the parking lot) or with a milestone not in the list come after all of them. Then the default order. Without `milestones` it is just the default order.

### 3.2 Touches — which files the work changes

`touches` lists paths or globs relative to the root of the code repository (not the backlog) that the work is expected to change. It answers one question: can two items hit the same file? Matching therefore errs on the side of an overlap:

- A pattern also covers everything below what it matches, as in `.gitignore`: `lib/foo`, `lib/foo/` and `lib/foo/**` are the same. Only a last segment that looks like a file name (a dot after its first character: `pubspec.yaml`, `*.dart`) without a trailing `/` stands for files alone.
- `*` and `?` match within one segment, `**` any number of segments (also none), `{a,b}` lists alternatives (commas inside braces do not split list values in `set`/`--touches`), `[...]` counts as any one character, `\` escapes.
- A leading `/` or `./`, empty and `.` segments are ignored; matching is case-sensitive.
- Two items overlap when some path is covered by a pattern of each. An item without `touches` overlaps nothing.

**Waiting for overlapping work.** An item in an `open` status whose `touches` overlap those of an item in an `active` status (in progress, review, … — the status counts, not the claim) is `conflicting` and waits for it, like a blocked item waits for its dependencies: it is not `ready`, so `next` (and a dispatcher built on `ready`) does not start it, and `claim` refuses it without `--force`. It becomes ready by itself when the active item is done, cancelled or released back to an open status. Active items never wait; two active items that overlap are a `touches-overlap` lint warning. Unlike `blocked`, this is not stored in a relation and does not need a cycle check: it only goes from open to active items.

**Files the active work really changed.** `touches` is an estimate; for an item in an `active` status the files its branch (`branch`, else `agent/<id>`) has changed since it forked from the base branch (`dispatcher.base`, default `main`) count as well, each as a literal path: `changed_files`, from `git diff --name-only --no-renames <base>...<branch>` (a rename counts with both paths) in the same repository as the branch heads (§3.1). They complete the item's `touches` when open items are checked for overlaps, so an active item without `touches` can hold up open items too. Only committed changes count. Without a repository, a base branch or the item's branch there is nothing to add. The diff of two head commits is remembered until one of them moves.

`lint` warns (`invalid-touches`) about an unclosed `[` or `{`, a stray `}`, a trailing `\`, `..` segments and patterns covering the whole repository (`**`, `*`, `.`).

### 3.3 Implementing an epic on one branch

An epic (any item with children; the type does not matter) can be implemented by one agent in one session on one branch (§8.2 *Implementing an epic*). `EpicPlan` (computed from a snapshot) describes that:

- **Members** — the items under it at any depth, in **work order**: an item comes after its dependencies and its children among the members, otherwise in the default order (§3.1); a cycle is cut where it is found.
- **State** of each member: `done` (done category), `handed-over` (an active status after the first one, e.g. `review`), `in-progress` (the first active status) or `to-do` (open). Only `to-do` members in a pickable status (`todo`) are taken; those in another open status (`backlog`, the parking lot) are **parked**: never next, not counted as *to do*, listed apart (`2 not taken (backlog)`) — informative, not a warning. A person decides what comes next by moving items to `todo`, also while the run goes on (each `--next` plans anew). A handed-over member counts as finished for the members after it: its work is on the epic's branch.
- **after** — the members a `to-do` member waits for: its dependencies and open children that are not done or handed over.
- **waits** — what outside the epic keeps a `to-do` member from starting: an unfinished dependency outside the epic (the epic's own `depends_on` count for every member) as `X-1 (todo)`, an open question (`a person's answer to its question`), an active item outside the epic its `touches` overlap (`X-2 (touches the same files)`; overlaps among the members do not count — one agent does them one after another), a live claim of another agent, an unknown status.
- **Verdict** — `forbidden` with **problems**: the epic is done, claimed by another agent, has no members, nothing left (every member done, handed over or parked: `… the rest waits in backlog: move what is next to todo.`), a dependency outside the epic that does not exist or is open but not pickable (not even planned), a dependency cycle among members; else `warning` with **warnings**: a dependency outside the epic that is planned (pickable or active) but not done, a member waiting for a person, overlapping work outside the epic, a member claimed (or in progress) by another agent, an unknown status, a `to-do` member after a parked one (a dependency or an open child: `X-3 depends on X-2 (backlog), which is not taken from backlog: move it to todo, or the agent stops there and asks.`); else `ok`. **Finished** — every member (in the scope) done, handed over or parked.
- **Next** — the member the agent goes on with: one `in-progress` that no other agent holds a live claim on, else the first `to-do` member without `after` and `waits`.
- **Branch** — the epic's `branch`, else `agent/<epic id>`.
- **Scope** — a run may implement one **milestone** only: then the members of that milestone and those without one are *in scope*, the others stay as they are (**skipped**: the unsettled ones outside the scope, `3 item(s) of other milestones stay`). Only members in scope can be next, and *nothing left* and *finished* count only them. An in-scope `to-do` member that comes after an unsettled member outside the scope (a dependency or an open child) is a problem (`X-1 (v0.2) depends on X-3 (todo) of v0.3, outside the scope v0.2: implement that milestone too (or all of it).`): the agent would wait for an item it never takes; the other direction does not matter. Without a milestone every member is in scope.
- **Progress** — per milestone of the members (in the workflow's order, those without a milestone last) how many are done or handed over of how many, whatever the scope (`v0.2 done, v0.3 1/4`).

## 4. Claims — parallel work without collisions

A claim is an agent's exclusive, time-limited lock on an item, stored as `.locks/<id>.lock` (JSON: item, agent, claimed_at, heartbeat_at, expires_at).

- **claim** — atomic create of the lock file; of two agents racing for one item exactly one wins, the other gets a conflict (exit 3). Claiming also sets `assignee` and moves an open item to the active status. Blocked items, items waiting for overlapping work (§3.2) and items with open children need `--force`.
- **heartbeat** — extends the lease (`lease_minutes`). Without heartbeats the claim **expires**; an expired claim can be taken over by another agent (atomic move-aside, again exactly one winner).
- **release** — drops the claim, returns an active item to the pickable status (or `--status`).
- **done** — sets a done-category status (default the first one, or `--status cancelled`), drops the claim, prints what got unblocked.
- Touching someone else's claim needs `--force`.
- `lint` reports `expired-claim`, `stale-claim` (lock on a finished item) and `orphan-claim` (lock for a missing item).
- Locks are machine-local (git-ignored): agents sharing one backlog folder coordinate through the filesystem.

Agent identity: `--as <name>` or `$BACKLOG_AGENT` (typically the worktree name).

## 6. Views — `views/<id>.yaml`

```yaml
name: Launch board
section: Releases          # optional heading in the app's view list
layout: kanban             # list | kanban | table | graph
filter:
  milestone: launch
  category: {not: [done]}
  or:
    - priority: [p0, p1]
    - labels: security
group_by: status           # any field; items with several values (labels) appear in each group
columns: [todo, in-progress, review, done]   # groups shown and their order
sort: [priority, -updated] # - = descending; rank = manual order (§3)
fields: [estimate]         # extra fields for cards/tables
```

### 6.1 Filter grammar

A mapping is an AND of its entries; `and: [...]`, `or: [...]`, `not: <expr>` combine expressions; `field: value` or `field: [a, b]` matches any of the values; `field: {in: [...]}`, `{not: [...]}`, `{exists: true|false}`, `{contains: text}` (substring of any value, ignoring case) refine it. A day as a value of `created` or `updated` (`created: 2026-10-31`) also matches the instants of that UTC day. `{within: <age>}` and `{older: <age>}` filter a time field (`created`, `updated`) by age, measured from when the snapshot is taken: at most / more than `<age>` ago, written `90m`, `24h`, `7d` or `2w` (`updated: {within: 7d}`, `created: {older: 30d}`); a day counts as its midnight UTC, items without the field never match, another age is a configuration error.

### 6.2 Fields

All front-matter keys (`id`, `title`, `type`, `status`, `priority`, `rank`, `milestone`, `parent`, `depends_on`, `related`, `assignee`, `branch`, `pr`, `labels`, `docs`, `touches`, `created`, `updated`), the computed `ready`, `blocked`, `conflicting`, `conflicts_with`, `claimed`, `claimed_by`, `needs_human`, `review` (`none`/`ok`/`changes`/`stale`, §3.1), `category`, `has_children`, `ancestors` (parent chain, cycle-safe), `epic` (epics among the item and its ancestors — `epic: X` selects everything under epic X), and any custom key.

### 6.3 Grouping

Without `columns`, groups come from the workflow (statuses, priorities, types, milestones, categories in their configured order), then other present values alphabetically, then "(none)". With `columns`, other matching items are counted as `hidden`.

Default views from `init`: **Board** (kanban by status, epics hidden, `sort: [rank, priority, created]`), **Ready to pick up**, **What's on fire** (p0/p1 not done), **Blocked**, **Dependencies** (graph).

## 7. Validation — `lint`

Errors and warnings with a code, item and location:

`unreadable` (broken file / front matter), `duplicate-id`, `file-name`, `unknown-status`, `unknown-priority`, `unknown-type`, `unknown-milestone`, `dangling-reference` (parent/depends_on/related to a missing item), `self-reference`, `dependency-cycle`, `parent-cycle`, `invalid-touches` (warning, §3.2), `touches-overlap` (warning: two active items with overlapping `touches`), `invalid-view`, `expired-claim`, `stale-claim`, `orphan-claim`, `dispatcher-worktree` (a dispatcher worktree path is not a folder), `dispatcher-agent` (warning: the agent's program is not on the `PATH`, or the profile is an unverified preset), `dispatcher-action` (warning: an action's program is not on the `PATH`, its agent is an unverified preset, or it can never run).

A broken `backlog.yaml` (including the `dispatcher` section) is not a lint issue: every command, `lint` included, fails with the configuration error (exit 1).

One server hosts several backlogs (*projects*): either every project of the registry (§1.2), or a single backlog folder.

| `--host` | | `0.0.0.0` | addresses to bind, repeatable or comma-separated (e.g. `127.0.0.1,10.77.1.2`) |
| `-p`, `--port` | | `8640` | |
| `--allow` | `BACKLOG_ALLOW` | everyone | client IPs / CIDR ranges allowed; others get 403 |
| `--token` | `BACKLOG_TOKEN` | none | require `Authorization: Bearer <t>` or `?token=` on `/api/` |
| `--generate-token` | | | random 22-char token, printed at start inside the URLs |
| `--web` | `BACKLOG_WEB` | built app next to the sources / bundled in Nix | static web app |
| `-q` | | | no request log |
| `--config` | `BACKLOG_SERVER_CONFIG` | `$XDG_CONFIG_HOME/kanban-ai/server.yaml` if it exists | the settings file below |

**Settings file** (`server.yaml`, `~/.config/kanban-ai/server.yaml` without `XDG_CONFIG_HOME`; edited in `backlog config` › Global › Server, §5): the values used where neither an option nor its environment variable is given — `host` (an address or a list, also comma-separated), `port` (1–65535), `allow` (IPs or CIDR ranges, a list or comma-separated), `token` (no spaces; `--generate-token` still replaces it), `web` and `projects` (paths: absolute, `~/…` or relative to the file; `projects` comes after `$BACKLOG_PROJECTS` in the order below) and `quiet` (boolean). Unknown keys or invalid values stop the start (exit 1); a file given with `--config` or `$BACKLOG_SERVER_CONFIG` must exist (exit 4), the default one may be missing. When read, the start prints `Settings from <file>`; the server reads it only at start.

**What is served**, first match wins: `--dir` (one folder; given together with `--projects` it wins and a note is printed), `--projects`, `$BACKLOG_DIR`, `$BACKLOG_PROJECTS`, `projects` of the settings file, the default registry file when it exists, the backlog found from the current folder (§1.1) as one folder. An explicitly given registry (`--projects`, `$BACKLOG_PROJECTS`) must exist; with nothing found the server exits with 4.

- **One folder** behaves as before the registry: the backlog must open or the server does not start; it is the default project and the only entry of `/api/projects` (id derived as in §1.2).
- **Registry**: only a malformed registry stops the start. A project whose folder is missing or whose `backlog.yaml` is broken is still listed, with its `error` in `/api/projects`; its requests fail with that error (`not_found` 404 without `backlog.yaml` or folder, `configuration` 500 for a broken one) and it recovers by itself once fixed (a missing folder is retried on every request). The registry file is watched: projects added, removed, renamed or reordered apply without a restart (a removed project stops its watcher and dispatcher and closes its event sockets); a malformed edit is logged and ignored, the previous projects keep running.

At start it prints the projects (id, path, the default one, errors), the web app and the board URLs (with the token). The web app is served with `Cache-Control: no-cache` and an ETag per file (derived from the build's location, size and time — files in the Nix store all share one date), so browsers revalidate and never keep files of an older build. A file of the web app with a compressed copy next to it (`main.dart.js.br`, `main.dart.js.gz`, made by the build) is sent as that copy when the client accepts its encoding, Brotli before gzip, with `Content-Encoding`, `Vary: Accept-Encoding` and an ETag per encoding; a copy older than its original is ignored, and range requests get the original. API responses of 1 kB or more are compressed with gzip when the client accepts it (`Accept-Encoding`; JSON shrinks 10–20×), with `Vary: Accept-Encoding`; smaller ones and WebSocket messages are sent as they are. Each project's folder is watched (debounced, ignoring `.git`, temp and editor files) and its change events go to its own WebSocket; edits from agents, `git pull` or an editor appear on the board immediately. `backlog.yaml` changes reload that project's workflow.

**Item cache.** The files stay the only source of truth; the server keeps the parsed item files of each project in memory so that a request does not parse every file again. Every request that needs the items (lists, details, views, lint, the dispatcher) still lists `items/` and `stat`s each file, and parses again only files that are new or whose stamp changed; deleted and renamed files drop out. A file's stamp is its modification time, change time (ctime) and size; a cached file is reused only when the stamp is unchanged **and** both times were more than 3 s older than the moment the file was read. File times have a coarse resolution (milliseconds, 2 s on FAT), so a file rewritten within the same tick with the same size keeps its stamp; such recently changed files are therefore read again on every request until they settle (and parsed only if their text differs). Restoring an old modification time (`touch -r`, `rsync -t`) still changes the ctime. Writes through the API drop the written file from the cache. Guarantees: a request answers from the files as they are when it starts, whoever changed them (API, CLI agents, editors, `git checkout`), without depending on the watcher; claims (`.locks/`) are read fresh on every request and derived state (blocked, ready, expired claims) is computed with the current time; an edit of `backlog.yaml` reopens the project and drops its cache; each project has its own cache. Not covered: a change that keeps size, modification time and ctime (only possible by changing the clock or with file systems that do not maintain ctime). The CLI reads all files every time (a short-lived process).

**Committing the backlog.** Agents change items through the CLI from their worktrees and never commit the backlog (their prompts and `backlog instructions` say so: the board commits it, its uncommitted changes are no problem to report). With `git.commit: auto` (the default) the server commits a backlog folder that is the top level of a git repository of its own — never one that lives inside another repository: after 30 s without changes (at the latest 5 min after the first change not yet committed), about 2 s after a run of an agent or action has ended, and when it stops. One commit takes everything that changed except claim locks (`.locks/`) and temp files (`*.tmp`, `*.stale`), with the subject naming the items and what happened to them — `new`, `deleted`, the new `status …` and `priority …`, `comment by …`, `note by …`, `review by …`, else `edited` (`Backlog: KA-7f3a status review, comment by wt-2; KA-9k2d new`; more than six parts end with `and N more`), and the paths in the body; the git identity is the repository's. With `git.push: true` it then runs `git push` (failures are logged, never retried by force). The log says `Backlog: committed 3 file(s): …` or why a commit or push failed. `git.commit: off` leaves it to people.

| `DELETE /api/dispatch/queue/<ref>` | | drops the queued start of the item (§8.2 *Queue of starts*); the new plan. `not_found` when none waits |
| `DELETE /api/dispatch/problems/<ref>` | | dismisses the problems of the item's last runs (§8.2 *Result and problems*); the new plan. `not_found` when there were none or no dispatcher runs |
| `POST /api/dispatch/epic` | `{item, fresh?, milestone?}` | starts one agent implementing the epic (§8.2 *Implementing an epic*; with `milestone` only the items of that milestone and those without one), in either mode; the new plan. `invalid_input` when the epic cannot be implemented (its problems) or belongs to an epic being implemented; when it is claimed, something runs for it or no worktree is free the start is queued (§8.2 *Queue of starts*) |
| `POST /api/dispatch/stop` | `{item}` | stops its agent (§8.2); the new plan; `not_found` when none runs |
| `GET /api/dispatch/log/<ref>` | `?lines=100` (1–2000) | `{item, path, running, lines[], last: {exit_code, reason, outcome, ended_at, session_id, result, problems[]}}` — the tail of the running agent's log, else of its last run; `not_found` when no agent ran |
| `WS /api/dispatch/log/<ref>/live` | `?lines=200` (1–2000), `?token=` | follows the agent log of the item like `tail -f` (checked every 0.5 s): messages `{"type": "agent-log", item, path, running, reset, lines[], last}`. The first one (`reset: true`) carries the last `lines` readable lines of the running agent's log, else of the last run (read from at most the last 512 KiB), or `path: null` and no lines while no agent has run; then each message carries the lines appended since (only complete lines while the agent runs), a change of `running` (with `last` once it ended), or `reset: true` with the tail of a new run's log. Lines are readable rather than raw: for `claude-stream-json` the assistant's text, one `▸ <tool> <command or path>` line per tool call, `  ✗ <tool>: …` for failed tool results and denied permissions, `! rate limit: …` when limited, `● Claude Code <version> · <model> · session <id>` at the start and `■ done · N turns · S s · $cost · session <id>` (or `■ failed (…)`) at the end; other JSON events (tool output, …) are left out, lines that are not JSON (the launcher's `# kanban-ai:` lines, stderr) pass through. Other outputs come as they are. `not_found` (no upgrade) for an unknown item or a project without a running dispatcher |
| `WS /api/events` | `?token=` | `{"type": "changed", "paths": [...]}` on file changes; `{"type": "dispatch", "paths": []}` when the dispatcher's plan changed (agent started or ended, worktree became busy, free or unavailable, …) |

Errors: `{"error": {"type", "message", "candidates"?}}` with `not_found` 404, `ambiguous_reference` 409, `invalid_input` 400, `claim_conflict` 409, `unavailable` 409 (e.g. no free worktree), `configuration` 500, `unauthorized` 401, `forbidden` 403. CORS is open (`*`) so the app can run from another origin.

### 8.2 Dispatcher

Every project runs its own dispatcher. With a `dispatcher` section in its `backlog.yaml` (§2) the server keeps a dispatch plan for it: after every change event (debounced again by 500 ms) and whenever a live claim expires (that frees a worktree or an item without touching a file) it takes a snapshot and computes

- **busy worktrees** — those with a live claim under their name or with an agent process still running in them; claims of other agents do not occupy worktrees and do not count against `max_agents`,
- **unavailable worktrees** — not busy, but no agent can start there: the folder is missing, it is not a git worktree, or `git status --porcelain` is not empty (uncommitted changes or untracked files). They are not free; the plan is evaluated again every 30 s while one is unavailable (worktrees are not watched),
- **replies** — unfinished, unclaimed items without a running agent and without an open question whose last agent session the configured agent can continue (see *Continuing a session*), with comments in the discussion written after that run started by anyone but the agent (its worktree name), notes (` · note`) and reviews (` · review …`) not counted: a person wrote to the agent; also such items **without a session to continue** (see *Replies without a session*),
- **assignments** — first the replies, each in its session's worktree, then ready items (§3.1) in the order of `backlog next` paired with free worktrees in the configured order (then those it created, then new ones, see below), at most `max_agents` minus the busy ones,
- **held** — ready items the dispatcher does not start by itself because their last agent ended without finishing, a person stopped it or their branch is checked out in a worktree the dispatcher cannot free (a manual start lifts the hold),
- **waiting** — ready items left over, and replies whose session's worktree is busy or unavailable (they wait for it), each with the reason it cannot start yet (no free worktree, `max_agents` reached, its session's worktree not free). In `manual` mode the assignments are only proposals and reserve nothing: an item they leave out has a reason only when it could not start by hand either (every slot of `max_agents` busy, no free or new worktree, its session's worktree not free); otherwise it is waiting without a reason and *Start agent* starts it.

The plan is logged whenever it changes (`Dispatcher (auto): 1/2 running; starts X-7f3a → monorepo-3; held: X-2c91; monorepo-2 unavailable: uncommitted changes (2 paths).`). In `auto` mode every new assignment goes to the agent launcher once (again only after it dropped out of the plan or its launch failed); in `manual` mode no new work starts by itself — only replies resume the agent they are meant for (below), the same assignments as in `auto` mode. Without the section the dispatcher is idle; edits of the section apply live. `-q` also silences the dispatcher log. Served from a registry, log lines start with `[<project id>]`.

**Worktrees on demand** (`dispatcher.repo`). The worktrees of the plan are the listed ones followed by those the dispatcher created earlier, recorded in `$STATE/worktrees/<project>/<name>.json` (name, path, clone, creation and last use; a record whose folder is gone is forgotten). Folders it did not create are never adopted, even when their names fit the pattern. While listed plus created worktrees are fewer than `max_worktrees`, the plan also has *new* worktrees: the names of `worktree_name` for n = 2, 3, … that are neither listed, nor recorded, nor held by a live claim, nor the worktree of an unfinished item's last session, and whose folder next to the clone (`<parent of repo>/<name>`) does not exist — always the first unused numbers, so names and paths are deterministic. Free existing worktrees are used first; an assignment to a new worktree is shown in the plan (`new`, `new_worktree`, log: `X-7f3a → monorepo-3 (new worktree)`) and, when it starts, `git worktree add --detach <path> <base>` runs in the clone first (nothing uncommitted is carried over), then the `setup` commands one after another in the new worktree (no shell, stdin closed, the server's environment, at most 15 minutes each; output in `$STATE/logs/<project>/worktree-<name>-<time>.log`) — e.g. `mise trust`, which agents may not run, and fetching dependencies, whose output must be ignored by git (the worktree must stay clean) — then the launcher continues as below with its branch. A failed `git worktree add` starts nothing (the reason is logged and returned by a manual start); a failed setup command (non-zero exit, not runnable, timeout) removes the new worktree again (`git worktree remove --force`, nothing is recorded or claimed) and fails the start the same way: `Cannot use the new worktree <name>: \`<command>\` exited with code 4 (log <path>)`.

**Cleanup** (only with `cleanup_after_days`): a created worktree that is free (no claim, no agent), clean (as above) and unused for that many days — counted from its creation, its last agent start or the last time it was seen busy — is removed with `git worktree remove` (never forced) when its checked-out commit is contained in `base` (merged, or no commits of its own); its branch is kept. Worktrees with unmerged commits stay until they are merged. A worktree that holds the last agent session of an unfinished item (see *Continuing a session*) is never cleaned up, however idle: a later start, a reply or the answer to the agent's question continues that session there and only there; it becomes eligible once the item is done (or deleted).

**Starting an agent.** The launcher (the same for every profile):

1. checks the worktree again (clean git worktree, see above; otherwise nothing starts and the reason is logged),
2. claims the item under the worktree's name — a claim conflict means someone was faster and nothing starts,
3. checks out the item's branch in the worktree: the item's `branch` field when set, else `agent/<id>`; an existing branch is switched to (a released item continues where its last agent stopped), a new one is created from `dispatcher.base` (default `main`) and recorded in the item's `branch` field. The agent does not have to manage branches; the prompt only tells it which one it is on (`{branch}`). **Branch in another worktree:** git checks a branch out in one worktree only; when another worktree has it (e.g. one where a `fresh` review of the item ran), the launcher detaches that worktree (`git switch --detach`) when the dispatcher manages it (listed or created), it is free (no live claim, nothing runs there) and clean, and goes on. Otherwise nothing starts: an agent's item is **held** with the reason (`<id>.hold.json` with `branch` and `worktree`) and gets one ` · note` by `kanban-ai` saying where the branch is stuck; that hold keeps even a reply from resuming the agent (it would fail the same way) and lifts by itself once the branch is no longer checked out there or that worktree can be freed (an earlier hold — the agent left it unfinished — then comes back; a reply still resumes it). A prompt action fails with `invalid_input` instead, which the dispatcher notes once and drops (§ *Actions*). Actions therefore leave the branch where it is when they end; the next start frees it. When this step fails otherwise, the claim is released and nothing starts,
4. starts the profile's command in the worktree as a **detached process** in its own session (it outlives a restart of the server), with stdin from `/dev/null`, stdout and stderr appended to `$STATE/logs/<project>/<id>-<UTC time>.log` (headed by the command), and the environment of the server plus `BACKLOG_AGENT`, `BACKLOG_DIR` and the profile's `env`,
5. records it in `$STATE/agents/<project>/<id>.json` (item, worktree, path, pid, process group, start, log, profile, output format, branch).

`$STATE` is `$KANBAN_AI_STATE_DIR`, else `$XDG_STATE_HOME/kanban-ai`, else `~/.local/state/kanban-ai`; `<project>` is the project id (§1.2). A small `sh` wrapper writes the exit code to `<id>.exit` next to the record and a closing line into the log.

**While it runs** the server checks every 5 s whether the process is alive (on Linux by `/proc/<pid>/cmdline`, which must still name the log) and renews its claim with a heartbeat every quarter of the lease (1–10 minutes). A restarted server picks the records up again, renews the claims at once and goes on watching.

**When it has ended**, the outcome depends on the item:

- still in the first active status, claimed by the worktree, after its agent worked on it again in a later active status (see *Who has the ball*) → **back to that status** (`review`), the claim dropped, no hold — whatever the run did (answered, asked, failed, was stopped); the pull request safety net below applies,
- still in the first active status (`in-progress`) and claimed by the worktree → **released** to the pickable status and **held** with the reason (`<id>.hold.json`), so that `auto` mode does not start it again in a loop (failures and rate limits are not retried; a person looks and starts it again),
- still in the first active status, claimed by the worktree, and the agent asked a question (`needs_human`) → only **released**, not held: it is not ready until somebody answers,
- in another status while claimed by the worktree (the agent ran `backlog set <id> status=review`) → only the **claim is dropped**; status and assignee stay. **Pull request safety net:** when that status is `active` (e.g. `review`), `dispatcher.pr` is configured, the item's `pr` is empty and its branch has commits not in `base` (`git rev-list base..branch`), the launcher does what `backlog pr` does (§5) in the worktree, with the agent's last message as the description (the `result` of a `claude-stream-json` log), else the agent's last comment, else the default description; the outcome is a ` · note` by `dispatcher` in the discussion (`… pushed agent/X-7f3a and opened <url>`, or `Could not open a pull request for …: <reason>` — the item then stays where the agent put it, `backlog pr` retries), so it wakes nobody; a branch without own commits gets a note and no pull request,
- done, released or claimed by someone else → left alone.

The record is replaced by `<id>.last.json` (exit code, reason, outcome, end time and, for `claude-stream-json`, the `session_id` of the run — a resumed run that reports none keeps the one it continued); the outcome is also appended to the log and logged by the server. Logs are kept.

**Result and problems.** `<id>.last.json` (and `<id>.action.json` of an action, see *Actions*) also keeps the agent's final message as `result` (the `result` of the last `result` event of a `claude-stream-json` log; null for other output) and what went wrong as `problems` (a list, empty when the run went well): a failed exit that no person caused (`the agent exited with code 1`, `… ended without an exit code (killed?)`; for actions `the action "Tests" exited with code 3` or a failed built-in), an error ending (`is_error` of the `result` event: `the agent ended with an error (error_max_turns)`), denied tool calls (its `permission_denials`: `2 tool calls were denied: Bash(git push …), WebFetch`) — but only when the run did not succeed (a failed exit, an error ending, an unrecorded review, the item left unfinished in the first active status); after a run that went well (e.g. exit 0 and the item handed over: the agent found another way) they are only a notice, in `notices` of the record and at the end of its log line (`# kanban-ai: the agent exited with code 0; it handed over as review, claim dropped (a tool call was denied: Bash(git -C …))`) — and a pull request the safety net could not open (`opening its pull request failed: …`). The latest run of an item is the one of the two files that ended last, except that the problems of the item session's run (`<id>.last.json`) hold until its next run: an action that ends after it without problems (e.g. the AI review `on_enter` of `review`) leaves that run the latest, one with problems adds them to its own (the log and `result` are the action's). The plan lists unfinished items whose latest run has problems as `problems` — unless something runs for them now or they are held (the hold says why already); they **need a person** (Dashboard *Needs you · Problems*, the agent box of the detail, the card). A new run of the item replaces them; finishing the item makes them go away. A person who dealt with them **dismisses** them (`DELETE /api/dispatch/problems/<ref>`, *Dismiss* in the agent box): both files keep them as `dismissed_problems` with `problems` empty, so they no longer show (`Dispatcher: the problems of X-1 were dismissed.`).

**Who has the ball.** The status says who works on an item: the first active status (`in-progress`) that an agent (or a person) changes it, a later active one (`review`, …) that it waits for somebody else. So when the item's own agent works on an item in a later active status again — a reply resumes it (a person's comment, a failed merge's comment), a fix round of an AI review, a manual start — or an action with `changes_code: true` runs on one, the launcher moves the item to the first active status before the agent starts and keeps the status it came from in the record (`return_to`). The prompts' `{handover}` is that status, so the agent hands its work back there (`backlog set {id} status={handover}`, or what the comments ask for); when it ends with the item still in the first active status it goes back there by itself (above). A start that fails restores the status. Actions that change no code (an AI review, commands, built-ins) leave the status alone. Leaving the status drops the `on_enter` actions queued for it, and handing the item back is a new transition (*Hooks*).

**Continuing a session.** The plan knows the session of each unfinished item's last run (from `<id>.last.json`). When the profile can resume (it has `resume` and output `claude-stream-json`), the session was run by the same profile and its worktree is free, a start of the item continues it **in that worktree** (agents keep sessions per folder): the command gets the profile's `resume` arguments and the prompt is `resume_prompt` with `{news}`. Assignments of other items leave such a worktree to the item when another free worktree (or a new one) exists — for ready items and replies later in the plan, and for items whose agent asked a question that waits for an answer (`needs_human`). When the session's worktree is busy or unavailable, or the profile cannot resume, a ready item starts a new session in any free worktree. A manual start with `fresh` always starts a new session. A session never continues in a *new* worktree (§ *Worktrees on demand*): new worktrees only take new sessions, after every free existing one that no waiting session needs. **When the session's worktree is gone:** a created worktree whose folder disappeared (removed by hand; cleanup never removes it, see above) is forgotten, and with it the session — the plan no longer lists it in `sessions`, the next start of the item is a new session in any free or new worktree, and a reply on an item that is not ready (e.g. `review`) starts a new session (see *Replies without a session*; the discussion stays in the item, so the new session sees it via `backlog show`). A *listed* worktree that is missing is only unavailable (§ above), so its sessions and replies wait for it.

**Replies resume the agent.** A reply (above) is assigned like ready work, but before it, whatever the item's status (`review`, `todo` after a question, …) and even when it is held (the reply is the person's go-ahead; not when the hold is for its branch being stuck in another worktree, see *Starting an agent*): it always continues the session in its own worktree, and its `{news}` lists the new comments — notes and reviews written since the run included, as context (reviews also when written under the agent's own name) (followed by `Comments marked "note" are context for you; they need no answer.`). A note or a review alone never resumes the agent, nor does it answer its question; it only reaches the agent with the next resume for another reason (a reply, a manual start). It starts by itself in `auto` and `manual` mode alike (`manual` only keeps the dispatcher from taking new work; a reply is an explicit instruction), within the usual limits — the session can be continued, its worktree is free, nothing else runs for the item, `max_agents`; a manual start starts it as well, also when the item is not ready. The resumed agent answers with `backlog comment` and either stops (a question about its work) or continues (an answer to its question, a change request). Once it started, the comments are older than its session and no longer count, so nothing loops; a person's comment while it runs is picked up after it ends. An item in `review` shows in progress while the resumed agent works and goes back to `review` when it ends without handing the item over itself (*Who has the ball*); the claim follows the usual rules. The log head and the server log say `resuming session <id>`; the record keeps it as `resumed`.

**Replies without a session.** When no session of the item can be continued — none is known (the item was worked on elsewhere, `<id>.last.json` is missing), its worktree is gone, or another profile ran it — a reply starts a **new session** of the configured agent under the same rules (first in the plan, any status and hold, `auto` and `manual` alike, a manual start too). Replies are the comments of others (not notes, not reviews) since the item's last agent start (`started_at` of `<id>.last.json`, kept also without a session id); when no start is known, only an item in an `active` status (`in-progress`, `review`, …) with a `branch` counts, with the comments after the last one of its `assignee` (all, when it never commented). This covers a failed merge's comment of the dispatcher on an item from elsewhere. The worktree: a free one that has the item's branch checked out, else any free (or new) one (a branch held by another idle worktree is freed at the start, see *Starting an agent*). The prompt is `resume_prompt` with `{news}` saying there is no earlier session (run `backlog instructions`, read the item and the branch's commits) and listing the new comments (notes and reviews as context). The item keeps its status; the assignment's key ends with `+reply`. Once it started, its start is newer than the comments, so it runs once.

**Implementing an epic.** A person starts one agent for a whole epic (§3.3) — any item with children — by hand (`POST /api/dispatch/epic`, *Implement epic* on the board), in either mode; the dispatcher never starts one by itself. The start re-plans and checks the epic's `EpicPlan`: `forbidden` refuses with its problems (`invalid_input`), warnings are for the caller to confirm (the board asks); a claimed epic is `claim_conflict`, something running for it or no free worktree `unavailable`. The agent is the configured `dispatcher.agent`; it continues the epic's last session in its worktree when it can (unless `fresh`), else starts where the epic's branch is checked out or in the first free (or new) worktree. The launcher claims the **epic** (with its open children, like `claim --force`), so it goes to `in-progress`, checks out the epic's branch (`branch`, else `agent/<epic id>`) and records the run with `epic: true` (also in `<id>.last.json`; later runs of the epic's own agent — replies, fixes of an AI review — keep it, and so does a prompt action that is not `fresh` when its run becomes the epic's last session). The prompt (whatever `prompt`/`resume_prompt` say) tells the agent who it is, the epic and branch, then: run `backlog epic <id> --next` (it claims the next item onto the branch), implement it in small commits containing the item's id, tick its checklist with `backlog check`, `backlog set <item> status=review`, repeat; when nothing is left, finish the epic — without `dispatcher.pr` `backlog set <epic> status=review`, with it one pull request for the whole epic (`backlog pr <epic> --description …` listing the items, then review); when nothing can start but items are left, `backlog ask <epic> "<what blocks, what is done>"` and stop; questions about an item go to the epic too; plus the talking and running rules. A resumed session gets `Since your last run: {news}` instead of the first step, a new session for replies the `{news}` of *Replies without a session*. **Limited to a milestone** (`milestone` of the start): the plan is checked with that scope (§3.3 *Scope*; an unknown milestone is `invalid_input`), the prompt says *the items of the milestone v0.2 and those without a milestone (leave the others as they are)* and every `backlog epic` in it carries `--milestone v0.2`; the run records `milestone` (also in `<id>.last.json`), so that later runs of the epic's own agent — replies, a new session for them, actions continuing its session — keep the scope, and a reply goes to *Repairing an epic* once every item of that milestone is handed over or done, even with items of other milestones left. The branch stays the epic's: a later run (another milestone, or all) continues on it while it is not merged; once a part was deployed (§8.2 *Merging*, *an epic deployed in part*) the next run starts the branch anew from `base` with a new pull request. A start without a milestone implements all of the epic.
- **While an epic is implemented** (an unfinished item with an epic run, running or last): the items under it belong to its agent: the plan never assigns them (not as ready work, not for replies, not in `held`), a manual start of one is `invalid_input` (`… belongs to the epic E, …; start E instead`), and `on_enter` actions queued for them are dropped (`it belongs to the epic E, which is reviewed and merged as a whole`). A manual start of the epic itself goes on as the epic. Replies on the epic resume its agent like any reply, with the epic prompt. **Repairing an epic:** a reply on an unfinished item with open children and a `branch` whose items are all handed over or done (`backlog epic` has nothing left; e.g. the comment of a failed merge of the epic) starts its agent on the epic's branch like any reply — automatically in manual mode too, without Implement epic, whether or not an epic run is known: it continues the epic's last session in its worktree when it can, else a new session goes where the branch is checked out, to a free or a new worktree. The run is an epic run (key `+epic+repair`) with the repair prompt: take no items, do what the comments ask — typically rebase on `dispatcher.base`, resolve the conflicts (`git add`, `git rebase --continue`), check, `backlog pr <epic> --force` — leave every status as it is (the epic stays in `review`; a person deploys it again), and when a conflict is beyond it or not clear-cut `git rebase --abort` and `backlog ask` on the epic. A manual start of such an epic without replies is `invalid_input` (nothing left to implement). Any other reply on an unfinished item with open children that no agent implements as an epic starts nothing (no assignment, no proposal): it waits with the reason `it has open child items: start Implement epic to take the reply up`, and a manual start of it is `invalid_input` pointing to Implement epic, whose new session reads the discussion. The heartbeat also renews the agent's claims on the epic's items.
- **When the epic's agent has ended**, its claims on items under the epic are dropped first: an item still in the first active status is released to the pickable status (the next run takes it up again), one handed over keeps its status and gets the epic's branch as its `branch` when it names another (or none) — its work is there, and its review and the merge go by that field (`backlog epic --next` sets it already) (`released the unfinished X-2; dropped the claims on X-1` in the outcome). Then the epic itself is handled like any item: in review → claim dropped (and the pull request safety net), a question → released, otherwise released and held.
- The epic's own `on_enter` actions run as usual: an AI review on entering `review` reviews the whole branch, i.e. the whole pull request.

**Stopping** sends `SIGTERM` to the agent's process group (`SIGKILL` after 5 s); the item is then released and held as above ("stopped by a person"). Stopping an action's agent or command only ends it (the item keeps its status, see *Actions*); built-in actions cannot be stopped (`invalid_input`).

Two servers hosting the same project share `$STATE` and would both look after its agents; run one.

**Queue of starts.** A start a person asks for — *Start agent* (`POST /api/dispatch/start`), *Implement epic* (`POST /api/dispatch/epic`), an action (`POST …/actions/<name>`, `backlog action`) — that cannot happen now because of something that passes (no free worktree, `max_agents` reached, something already runs for the item or holds its claim, its branch checked out in a busy worktree, the worktree not ready) is queued instead of refused; one that can never happen (the item done, cancelled or not ready, open children without Implement epic, an action its status does not offer, an unknown action) is refused as before. The queue is kept in `$STATE/actions/<project>/state.json` (`queue: [{item, kind: agent|epic|action, action, fresh, milestone, by, since, reason}]`, `milestone` for an epic limited to one), so it survives a restart; one entry per item (a new request replaces the item's entry in its place). Every evaluation, in either mode, first wakes agents for replies (a person's comment, a failed merge), then starts what is queued in queue order — each as soon as it can — and only then new work (`auto`); an entry that started leaves the queue, one that cannot start yet stays with the reason of the last attempt, one that can no longer start is dropped with a note (`The queued start (Start agent) was dropped: …`). The plan shows the queue as `queue: [{item, title, kind, action, fresh, by, since, reason, position}]` (`reason` what it waits for by the current plan, `position` from 1); `DELETE /api/dispatch/queue/<ref>` cancels an entry. The log says `Dispatcher: queued Start agent for X-1: No free worktree …` and `… the queued Start agent for X-1 started (…)`.

**Actions** (`dispatcher.actions`, §2) run on one item, either because a person asks (a button on the board, `POST …/actions/<name>`, `backlog action <id> <name>`; only actions the item's status offers) or as a hook (`on_enter`), in `auto` and `manual` mode alike (hooks are explicit rules; to switch one off, remove its `on_enter`). An item has at most one run at a time: while its agent or another action runs, a request fails with `unavailable` and a hook waits.

- **Prompt actions** start an agent through the launcher above, with the action's profile. The worktree: the one of the item's last session when the profile can continue it there and the action is not `fresh` (the command gets the `resume` arguments); else the free worktree that has the item's branch checked out, then the free worktree of its session, then any free (or new) one — within `max_agents`. The agent claims the item under the worktree's name **without changing the item** (status and assignee stay — except the status with `changes_code`, see *Who has the ball*; done items too), the branch is prepared as usual, and the prompt is the action's text in a fixed frame: who and where the agent is, that the item stays in its status unless the action asks otherwise (never `in-progress`; with `changes_code`: that it shows in progress while the agent works and goes back by itself), the item's context (`backlog show`, or `Since your last run: {news}` when continuing) to comment only when the action asks for it (then in exactly one comment) or to answer a person's question, and otherwise to finish without a comment (or to ask with `backlog ask` and stop), plus the talking and running rules above; it never runs `git push` — with `dispatcher.pr` it publishes its commits with `backlog pr {id}`, which updates the item's pull request (e.g. after fixing review comments). **AI review** (`review: true`): the action's text is a built-in task instead — review the changes of `{branch}` against `{base}` (`git log`/`git diff {base}...{branch}`, the pull request `{pr}` when set), read the item, its discussion and the project's contributor rules (CLAUDE.md, AGENTS.md, CONTRIBUTING.md, README.md), check correctness, tests, documentation, security and scope; change nothing (no edits, commits, pushes, item changes), approve nothing; findings only for real problems, as a numbered list — followed by `Also: <prompt>` when the action has a `prompt`; the frame then asks to finish with `backlog review {id} --ok "…"` or `backlog review {id} --changes --file .kanban-ai/review-{id}.md` (the findings written with the Write tool first; a command spanning lines would be denied) — its one comment, in the language of the people in the item — instead of the comment rule, and never to push, also with `dispatcher.pr`; the talking and running rules apply as well. At the end the claim is only dropped — never released or held, whatever the status — and, only when the agent failed, a note goes into the discussion (`### kanban-ai · … · note`: `The action "AI review" (agent claude in wt-2) exited with code 1 after 3 min.`). A review action whose agent recorded no review comment since it started (and was not stopped by a person) gets such a note too (`… It recorded no review (\`backlog review\`), so the review is lost; run the action again.`) and the problem `the review was not recorded (no \`backlog review\`)` (*Result and problems*). A continued or non-`fresh` run is recorded as the item's last session (`<id>.last.json`, see *Continuing a session*); a `fresh` run is a side session recorded in `<id>.action.json` and the item keeps its own session (a reply resumes that one). An action never lifts a hold.
- **Commands** run detached like agents (same `sh` wrapper, record and log, stdin from `/dev/null`, environment of the server plus `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=true`, `BACKLOG_DIR`, `KANBAN_AI_ITEM`, `KANBAN_AI_ACTION` and, in a worktree, `BACKLOG_AGENT=<worktree>`), **in the free dispatcher worktree that has the item's branch checked out** (it stays busy meanwhile; uncommitted changes do not matter), else in the primary clone `dispatcher.repo` (`{worktree}` empty); with neither the command cannot run. Nothing is claimed and the item is not changed. When it has ended, a note gives the exit code, the duration and the last 20 lines of its output (in a code block). The record of the run is `<id>.action.json`.
- **Built-in actions** (`run: <name>`) run inside the server, in the same place as a command (the backlog folder when there is neither), with their own log; they cannot be stopped and a restart of the server while one runs ends it as `interrupted`. Their result (`succeeded: …` / `failed: …`) is the note. Built in: `noop` (does nothing, for trying actions and hooks out), `merge` and `preview` (below). Implementations get the item, the action, the configuration, the backlog's services, the working directory, the placeholders and a way to run programs into the log (`BuiltInAction` in `backlog_core`); every name `backlog.yaml` accepts has one.
- **Merging (`run: merge`, `dispatcher.merge` §2)**, typically `on_enter: deploy` (with a `deploy` status of category `active` after `review`), optionally also a button in `review` (`statuses: [review]`). The branch is the item's `branch` field, else `agent/<id>`; the primary clone is `dispatcher.repo`, else the main worktree of the item's (or the first listed) worktree. Strategy **`local`**: in the free dispatcher worktree that has the branch checked out, else in a temporary worktree `<repo>-merge-<id>` next to the clone (added for the merge and removed afterwards; a branch checked out anywhere else is refused), which must have no uncommitted changes to tracked files: unless the branch already contains `base` it is rebased onto it (`git rebase <base>`), then `check` runs there; with `push` the result is pushed to `<remote>`'s base (`git push -- <remote> <commit>:refs/heads/<base>`, never forced; refused when the remote base moved on); finally the base is fast-forwarded where it is checked out (`git merge --ff-only`, usually in the primary clone, which is checked first for uncommitted changes to tracked files — untracked files do not matter) or, checked out nowhere, its ref is moved (`git update-ref`). Strategy **`pr`**: `pr.merge` runs where the action runs (`{pr}`, `{pr_number}` from the item's `pr`; without one nothing is merged). Strategy **`command`**: `merge.command` runs there; exit code 0 means merged. **Success:** the item gets the first `done` status (like `backlog done`) and so do the unfinished items under it whose `branch` is the merged branch (an epic implemented on one branch, §8.2 *Implementing an epic*; the note says `X-1 is done; with it X-2, X-3`). **An epic deployed in part** — unfinished items remain under it (todo or backlog items without work on the branch, items on another branch) — is not done: it goes back like after a failure (a hook: to the status it came from when `active`, else the closest `active` status before the hook's; a button: it stays), loses its claim and its `pr` (merged; the next *Implement epic* starts a new branch from `base` and opens a new pull request) and the note says `deployed 2 item(s) (X-2, X-3), remaining 1 (X-4); X-1 stays open and went back to review, the next Implement epic starts a new branch from main`; it is done by the deploy that leaves nothing under it. Then with `cleanup` the worktree that has the branch checked out is removed (`git worktree remove`, never forced) when the dispatcher created it, switched to `base` (detached) when it is listed, and left alone when it is the primary clone, any other folder or has uncommitted changes or untracked files; the branch is deleted (`git branch -D`) when it is no longer checked out and loses nothing — it is contained in `base` or is exactly what its remote-tracking branch `<remote>/<branch>` says (everything was pushed into the pull request) — else kept with the reason; and the session id is removed from `<id>.last.json` (`session_dropped`), so nothing continues it. The result note says what happened (`The action "Merge" (wt-2) succeeded: merged agent/X-7f3a into main (fast-forward, rebased onto main, checked); X-7f3a is done; removed the worktree wt-2; deleted the branch agent/X-7f3a; dropped the agent session after 4 s.`). **Failure** — a rebase conflict (`git rebase --abort`), a failing check, a refused push, fast-forward or `pr.merge`/`command`: the branch is reset to the commit it had (a rebase never stays half done) and the base is untouched; a hook moves the item back to the status it came from (remembered with the transition) when that is an `active` one after the first (from `in-progress` an agent just fixed it, *Who has the ball*), else to the closest such status before the hook's status (the first `active` one when there is none) (a plan may have seen the item last in `todo` when its agent set `review` just before a person moved it on) — a button leaves it where it is — and a **comment** by `kanban-ai` (not a note: the item's agent session continues with it like with any reply, in either mode) says what failed with the end of the output and how to fix it, as numbered steps in the worktree of the branch, each a command the `claude` profile's whitelist allows: `git fetch <remote>` (for `pr` and `command`), `git rebase <base>` (`<remote>/<base>` for `pr` and `command`), resolve the conflicts, `git add <file>`, `git rebase --continue` (never `--abort`/`--skip`), run `merge.check` (or the project's checks) and commit, `backlog pr <id> --force` when `dispatcher.pr` is set (never `git push`), then — for a hook — `backlog set <id> status=<hook's status>` to merge it again, unless a person has to decide something (how to resolve a conflict, a check it cannot fix): then leave the item where it went back and ask with `backlog ask`; for a button: leave the status, then run the action again. **An item on its epic's branch** — its branch is the branch of an ancestor (that ancestor's `branch`, else `agent/<ancestor>`) and other unfinished items under that ancestor have the same `branch` — is not merged (that would bring their work along while they stay unfinished): it goes back as after a failure, with a note `… failed: this work is on the branch agent/X-1 of the epic X-1 together with X-3, X-4; deploy the epic X-1 instead (move it to deploy). Nothing was merged.`; the only item on that branch is merged as usual. Problems of the setup — no primary clone, uncommitted changes where the base is checked out, the branch checked out elsewhere, no `pr`, a missing branch — only get a note (nothing for the agent to do). The action runs inside the server like every built-in (it cannot be stopped; a `check` has no time limit).
- **Deploying locally (`run: preview`, `dispatcher.preview` §2)**, typically a button *Deploy locally* in `review` (`statuses: [review]`; items and epics alike): the board runs from the item's branch rebased onto `base` without merging anything — the branch and its pull request stay as they are. The branch is the item's `branch`, else `agent/<id>`; the primary clone as for `merge`. In the helper worktree `preview.worktree` (default `{repo}-preview`, next to the clone; added with `git worktree add --detach` on first use; an existing folder must be a detached worktree of the clone that is neither the clone itself nor a worktree of the dispatcher, listed or created — else the preview fails with `… is not the preview's helper worktree: it has the branch x checked out; nothing was changed there` — and `backlog.yaml` refuses a `worktree` that names the clone (`{repo}`) or a dispatcher worktree; there an unfinished rebase is aborted and `git checkout --force --detach <branch>` replaces what an earlier preview left) a copy of the branch (detached HEAD) is rebased onto `base` unless it contains it, then `check` and `install` run there (placeholders `{id}` `{title}` `{branch}` `{base}` `{path}` = the preview worktree, `{repo}`, `{backlog}`; no time limit). With `server` the server checks first that the program runs (`<server> --help` exits with 0), records the preview in `$STATE/preview.json` (project, item, title, branch, commit, base, since, server, main_server — `main_server` is `preview.main_server`, else the program the server runs as; a preview started from a preview keeps the main server of the first) and, once the action has ended and its note is written (`The action "Deploy locally" (backlog) succeeded: deployed the preview of X-7f3a: agent/X-7f3a at 1a2b3c4d5e6f (rebased onto main, checked, installed); the server restarts as backlog-server-dev after 2 min.`), **restarts**: a detached helper (`sh`) waits until the server process has ended, then starts `server` with the same arguments, working folder and environment — without `BACKLOG_WEB` (each build brings its own web app; `--web` among the arguments still applies), with `KANBAN_AI_SERVER_PROGRAM` = the program and `KANBAN_AI_PREVIEW` = the commit — its output appended to `$STATE/server.log`; the old server stops right after starting the helper. The new server runs detached from the terminal the old one was started in; agents and commands keep running and the new server finds them (above). A server runs a preview when `KANBAN_AI_PREVIEW` matches the commit in `preview.json` (a server started by hand, or another server sharing `$STATE`, does not). Without `server` the preview is only prepared (the note says so) and nothing is recorded. **Failure** — no primary clone, a missing branch, a rebase conflict (`git rebase --abort`; the note says `deploying the preview failed: conflict in lib/a.dart (rebasing onto main)`), a failing `check` or `install`, a `server` that does not run or a server that cannot restart itself: the running server and the recorded preview stay as they are. Only one preview is prepared at a time (another one fails with `another preview is being prepared`); a new preview replaces the previous one. **Back to main** (`POST /api/preview/main`, the board's banner) forgets the preview and restarts the server the same way as `main_server` (without `KANBAN_AI_PREVIEW`).
- **Pull requests merged elsewhere** (`pr.state`): every `state_every` minutes (default 2, counted per project; the check runs beside the 5 s watch of the agents) the server runs `pr.state` in the primary clone (else the backlog folder; at most 30 s each) for every item in an `active` status with a `pr` that is not claimed and has nothing running, and reads its output: JSON (an object or the first of a list) with `merged: true`, a non-empty `merged_at`/`mergedAt` or `state`, else the first of the words `merged`, `closed`, `open` (any case). **Merged** → the item gets the first `done` status (with the items under it on its branch, as after `run: merge`; an epic with unfinished items left stays in its status without its `pr`, the note says `… X-1 stays open in review; deployed 1 item(s) (X-2), remaining 1 (X-3); …`) and is cleaned up as after `run: merge` (with `merge.cleanup`), with a note (`The pull request <url> was merged outside the board; X-7f3a is done; removed the worktree wt-2; deleted the branch agent/X-7f3a.`). **Closed** without merge → one note per pull request (`… was closed without being merged; X-7f3a stays review.`); the item stays. Anything else (open, a failing command, unreadable output) changes nothing and is logged. What it saw last is kept in `$STATE/pull-requests/<project>/<id>.json`. Examples: `gh pr view {pr} --json state --jq .state` (GitHub), `tea api repos/{{owner}}/{{repo}}/pulls/{pr_number}` (Gitea; `tea api` fills in owner and repository itself, `{{…}}` keeps the braces).
- **Hooks (`on_enter`).** Every plan compares the status of each item with the status it had in the previous plan; an item whose status changed to an action's `on_enter` status queues that action **once per transition** (a later change back and forth queues it again). Items seen for the first time (new items, the very first plan) trigger nothing. Statuses and the queue are kept in `$STATE/actions/<project>/state.json`, so a restarted server neither repeats a hook nor forgets one queued or caused while it was down (it compares with the statuses it saw last). A queued action starts as soon as nothing runs for the item (e.g. right after the agent that moved it to `review` has ended) and, for a prompt action, the item is not claimed and a worktree is free; it is dropped when the item leaves that status first, is deleted or the action is removed — an AI review (`review: true`) also when, at the moment it could start, the latest review comment already saw the current head of the item's branch (review state `ok`/`changes` with a known head, §3.1; logged, no note): the item came back without new commits (e.g. after a failed merge). A button or request always runs it. A hook that cannot start for another reason (a command without a place to run, an unknown item, the branch checked out in a worktree that cannot be freed) is dropped with a note; the item keeps its status — a start that fails changes nothing (an action's agent drops the claim it took, the item's own agent gives the item back in the status it had). In `auto` mode hooks start after the ready work of the same plan. The plan shows them in `pending_actions`; the log says `Dispatcher: X-7f3a entered review; queued the action "AI review".`
- **Review ↔ fix loop** (`auto_fix: N` on an AI review, in `auto` and `manual` mode alike, like hooks). A review comment alone never wakes the item's agent (§3); this explicit rule does. When such a review starts (by hook, button or request) the dispatcher records a loop for the item in `state.json` (`loops: [{item, action, round, phase, since}]`; a running loop keeps its round count, a new one — or one after an exhausted loop — starts at 0) and, whenever nothing runs or is queued for the item, moves it on: after the review, a verdict newer than its start that is `ok`, or no verdict at all, ends the loop; `changes` starts the item's **own agent** (the configured `dispatcher.agent`, not an action: it claims the item as usual — an item in `review` shows in progress meanwhile, *Who has the ball* — continuing the item's session in its worktree when it can, else a new session where the item's branch is checked out or in any free or new worktree; it waits for a free worktree and an unclaimed item) with a fixed prompt: who and where it is, the item shows in progress while it works, `automatic fix round r of N`, fix the findings in small commits containing the id, say why in exactly one comment where a finding is wrong (what was fixed belongs in the commits), publish with `backlog pr {id}` (with `dispatcher.pr`, else never push), run `backlog set {id} status=<status>` and stop, the talking and running rules, followed by the review's author, commit and text; a note says `The AI review asks for changes: started the agent in w1 to fix them (automatic round 1 of 2).` After the fix run has ended, new commits on the branch (the review is `stale`, §3.1) queue the review action again (`pending_actions`; it starts like a hook), no new commits end the loop with a note. When a review still asks for changes after N rounds the loop is *exhausted*: a note says `The AI review still asks for changes after N automatic fix rounds (auto_fix: N); a person decides now.` and nothing more happens until a review starts again. A loop ends as well when its item is done or gone (so a merge, §8.2 *Merging*, drops it), or the action loses `review`/`auto_fix`. **After a failed merge** the item goes back to `review`, which queues an `on_enter: review` AI review again, and the failure comment resumes the item's agent: the agent's resume starts first (in either mode) and the item shows in progress while it works, which drops the queued review. When the agent has fixed the branch it moves the item to the merge's status itself (the failure comment says so), which merges it again without another AI review; when a person has to decide, the item goes back to `review` (by the agent or by itself, *Who has the ball*), which queues the review again only for new commits (*Hooks*) — at most one agent works on the item at a time.
- **AI review in a status of its own** (`then`). With a status for it — e.g. `ai-review` of category `active` between `in-progress` and `review` — and the AI review on it (`on_enter: ai-review`, `then: review`), `review` always means that a person is needed. New work is handed over to the review's status (`{handover}`), the hook reviews it there, and when the review is over the dispatcher moves the item on to `then` by itself (logged): after an `ok` verdict or none, after `changes` without `auto_fix`, when the `auto_fix` rounds are used up (with the note above) and after a fix round without new commits — whenever the review loop (above; a review with `then` has one even without `auto_fix`) ends with the item still in the review's status — and also when the hook is skipped because the latest review saw the branch's head already. With `auto_fix` the fix prompt lets the agent decide: it fixes what it can and gives the item back to the review's status (reviewed again), or, when a finding needs a person's decision or it is not sure, leaves it, says so in one comment (or asks with `backlog ask`) and sets `then` itself, which ends the loop. Items reviewed in another status (the button in `review`) are not moved.
- **Requests of the CLI** wait as files in `<backlog>/.locks/actions/`; every plan takes them (oldest first) and starts them like a button: one that cannot start yet joins the queue of starts (below, `by` = who asked), one that can never start leaves a note on the item (`The action "Tests" (requested by tobik) could not start: …`).

**Manual start and stop** go through the API (§8.1) and the board (§9): a start re-plans first, takes the worktree of the session it continues or else the first free worktree (even one the plan proposes for a more urgent item) and launches as above; any ready item can start while fewer than `max_agents` run and a worktree is free or can be created — the proposals of other items reserve nothing. It works in `auto` mode too. Every published plan is also sent as a `dispatch` event over the project's WebSocket.

## 9. Web board## 9. Web board

URL parameters: `?token=…`, `&as=<name>` (agent name used when claiming from the UI, default `web`), `&server=http://…` (another API server).

**Projects:** the app loads `GET /api/projects` and opens the project named by the route after `#` (`/#/p/<id>`), else the one last opened in this browser (`localStorage`, per server origin), else the first available project; unknown and unavailable projects in the URL fall back the same way. The route always names the open project (a link can be shared and reloaded) and the page title is its name, prefixed with *(N)* while N things wait for a person in any project (*Dashboard* below). Each project gets a fresh session: its API (`/api/p/<id>/…`), theme, board, filters, open item and WebSocket; the previous project's are disposed. The session opens on the view last chosen in that project (picked in the navigation or just saved; `localStorage` key `kanban-ai.view.<id>`, `kanban-ai.view` for a single backlog), else the default view (`board`, else the first); a remembered view that no longer exists falls back the same way. A URL edited to another `#/p/<id>` switches to it. When `/api/projects` answers 404 (a server without projects) the app shows the single backlog on the unprefixed paths; other failures show the error with *Retry*; when no project can be opened their errors are listed.

**Layout** (responsive): from 1200 px a left panel with views (208 px, 240 px from 2000 px) and the open item as a panel on the right; 840–1199 px view tabs under the header (☰ opens a drawer with the full navigation) and the open item as a bottom sheet; below 840 px the open item is a full page; below 600 px the header has ☰ and a view dropdown and a bottom bar shows the pinned views (up to three; the first two views when none are pinned) plus *More* (the drawer). *New item* is a floating button outside the left panel. From 2000 px wide (27" 4K and similar) text is 15 % larger.

**Left panel**
- On top the open project's name; with more than one project it opens a menu: the pinned projects under *Pinned* (plus the open project under *Open* when it is not pinned), or all registered projects when none is pinned — the open one ticked, the others with a badge counting what waits for a person in them (*Dashboard* below); one the server cannot open greyed out with its error and not selectable — and at the bottom *All projects (N)…*, a dialog listing every project (path or error) with a search box from 8 projects; a click opens one, the pin button pins or unpins it for everybody (`PATCH /api/projects/<id>`). The drawer has the same switcher on narrower windows and phones.
- *New item* button (dialog: title, type, status, priority, milestone, parent, labels, body). The parent is optional and searched by id or title among unfinished items (epics and stories first); choosing one sets the type to its child type unless the type was picked by hand: epic → story → task → subtask, each only when the workflow has that type (a task without `subtask` gets a task; other types and missing levels the default type). The detail's *Add child* opens the same dialog under the shown item and opens the new item. Below 600 px the dialog is a full page (✕ cancels, *Create* in its app bar) that shrinks above the on-screen keyboard, so the field being typed in stays visible.
- *Dashboard* (above the views) with a badge counting what waits for a person in the open project; a click shows the project's dashboard in place of the current view (highlighted like a selected view; on medium widths it is also the first tab). Picking a view, a person or narrowing the board otherwise goes back to the board; a new session of a project opens on its view.
- Saved views with their item count; views with `section` grouped under foldable section headings; the ⋮ menu of a view moves it to an existing or new section (persisted to the YAML) or pins it to the phone's bottom bar.
- *People*: agents holding a live claim with how many items each holds (busiest first); a click narrows the board to that agent's items (the People filter).
- *Agents* (with a dispatcher, §8.2): heading *Agents · mode · running/max*; one row per worktree — the item its agent works on (or holds a claim on), *free* or *unavailable* (reason as tooltip) — a click opens the item; the plan's assignments (*X → w2*, with ▶ *Start* in `manual` mode), held items (reason as tooltip), the first three waiting items with their reason (*X waits: no free worktree*) and *N more waiting*. Reloaded on `dispatch` events.
- *Lint* summary at the bottom ("Lint: 2 warnings"); a click lists the problems with links to items.

**Dashboard** (per project, in place of the board: *Dashboard* in the left panel, the drawer or the tabs): what waits for a person and what goes on in the open project (the single backlog without projects). The app watches every available project for as long as it runs — items with the finished ones, the dispatcher's plan, lint and the open question of each `needs_human` item (`GET …/items/<ref>`), reloaded on its WebSocket's `changed` and `dispatch` events — so the page title counts across projects and the project switcher per project, whichever one is open. *N need you* = questions + items to approve + items with problems + held items. Its header (in place of the board's) says *Dashboard · N need you* and has reload (the menu below 1200 px); a project that cannot be loaded shows its error with *Retry*. Sections, two columns from 1000 px of the dashboard's width (*Needs you* left, *Running* and *Overview* right), else one column in this order:

**Preview banner:** while the server runs a local preview (`GET /api/preview`, asked at start and every 15 s — a preview restarts the server, no event announces it), a banner above the header of the board and on top of the dashboard says *Preview of X-7f3a running · agent/X-7f3a @ 1a2b3c4 · since 5 min ago* (the item's title, full commit, base and server program in tooltips) with *Back to main* (`POST /api/preview/main`; tooltip: the program it restarts as): the banner goes away and a notice says the server restarts and the page should be reloaded in a moment for the main build's board; a refusal is shown as a notice and the preview stays.

**Header** (56 px, top of the main area): the filter bar, then *Group: status ▾* (regroups the current view for the session by status, priority, type, milestone, assignee, labels or epic, or none; *The view's own* goes back; an asterisk marks a changed grouping; only an icon when the header is narrow), compact buttons for columns, theme and reload, and a loading indicator. `/` focuses the search when no text field has focus. No step while something runs or is queued for the item.

A chip reloads the check with `?milestone=` (the counts and items are those in the scope, *1 item(s) of other milestones stay as they are: X-4.*) and *Start* sends `milestone`. The progress per milestone shows when the epic has several (*v0.2 done · v0.3 1/4*). Parked items (§3.3, `backlog`) are listed apart (*2 item(s) are not taken from the backlog: X-5, X-6. Move what is next to todo, also while the agent works.*, *· 2 in backlog* in the counts, *· not taken* on the item) with a button *Move X-5 to todo* each, which sets the workflow's pickable status and checks again. ## 10. Installation and operation

- **Per project with mise** (recommended): `[plugins] nix = "https://github.com/jbadeau/mise-nix.git"` and `[tools] "nix:kanban-ai" = "github+Huholoman/kanban-ai#kanban-ai"` (optionally pinned `…/kanban-ai/<commit>#kanban-ai`); update with `mise install --force nix:kanban-ai`.
- **From a clone, per user**: `mise run install [ref]` (or `tool/install.sh [ref]`, default `main`; a branch, tag or commit of the clone) builds `git+file://<clone>?rev=<sha>` with Nix, out-link `~/.local/state/kanban-ai/release` (GC root) and symlinks `backlog`, `backlog-server` in `~/.local/bin`; `mise run install-dev` (`tool/install.sh --dev`) builds the worktree as it is (uncommitted changes of tracked files included) into `…/dev` and links `backlog-dev`, `backlog-server-dev`. Next to the out-link it writes what it built from and when (`release.txt`, `dev.txt`: ref, commit, clone or worktree, date), which the doctor of `backlog config` shows. `KANBAN_AI_BIN_DIR`, `KANBAN_AI_STATE_DIR` override the folders (state defaults to `$XDG_STATE_HOME/kanban-ai`). Prints the ref and commit it installed.
- **Nix flake**: `nix run github:Huholoman/kanban-ai`, `#server`; packages `kanban-ai` (CLI + server with the web bundled) and `web`; `overlays.default`.
- **NixOS module** `services.kanban-ai`: `enable`, `package`, `backlog`, `user`, `host` (string or list, default `127.0.0.1`), `port` (8640), `allow` (list), `tokenFile` (`BACKLOG_TOKEN=…`), `openFirewall`; runs a systemd service.
- **Without Nix**: Dart ≥ 3.8 and Flutter ≥ 3.32; `dart compile exe` the two entry points, `flutter build web --no-web-resources-cdn --pwa-strategy=none` the app and `tool/precompress.sh build/web` in `packages/backlog_app` (what `mise run build-web` does).
- **Web build** (Nix and `mise run build-web` alike): CanvasKit and the fonts (§9) are part of the build instead of Google's CDN; no service worker (the server's ETags keep the browser cache right; an empty `flutter_service_worker.js` replaces the worker of older builds); `.br` and `.gz` copies of the compressible files (`gzip -9`, `brotli -q 11` when `brotli` is installed) for the server to send (§8).

Agents get the workflow from `backlog instructions` (paste into CLAUDE.md / AGENTS.md): identify with `BACKLOG_AGENT`, `backlog next` or `claim`, `heartbeat` during long work, set `branch`/`pr`, give new items `touches`, `done` or `release`, split discovered work into new items, `lint` before stopping.

## 11. Architecture (for contributors)

Dart pub workspace (`backlog_core`, `backlog_cli`, `backlog_api`, `backlog_server`) plus the Flutter app outside it.

- **backlog_core** — hexagonal modules `workflow`, `items`, `claims`, `planning`, `dispatch`, `views`, `validation`, `projects` (the registry: `ProjectRegistry`, port `ProjectRegistryStore`, `ProjectService`, YAML store); pure `domain/`, use cases in `application/`, file-system adapters in `infrastructure/`; `storage` (port `BacklogStorage`: where a backlog is kept — configuration, action requests, the stores of items, claims, views and item history, and its changes (port `ChangeSource`, `FolderChangeSource` watches a folder); `FileBacklogStorage` is the folder; every storage passes the shared contract tests `test/storage_contract.dart`); `Backlog.connect` is the composition root over a storage (`Backlog.open` over a folder); derived state lives in `BacklogSnapshot`; `DispatchPlan` (pure) turns a snapshot into assignments, `Dispatcher` re-plans on changes and hands them to the `AgentLauncher` port, implemented by `ProcessAgentLauncher` (detached processes, state under `$STATE`; also the commands and `BuiltInAction`s of actions) behind `WorktreeProvisioner` (worktrees on demand: records, `git worktree add`, cleanup); actions: `ActionDefinition` (workflow), `DispatchPlan.actionStart` (where one runs), `ActionState` (status hooks, port `ActionStateStore`) and `ActionRequests` (requests of the CLI); `settings` (editing configuration files: `ConfigDraft` — edits through `yaml_edit`, key paths, typed values, `diffHunks` — port `ConfigFile`, use case `ConfigEditor` — open, problem, save with a check for changes made meanwhile — and the file adapter with `projectConfigEditor` / `registryConfigEditor`).
- **backlog_cli** — thin adapter; text and JSON renderers; `tui/` — the terminal UI of `backlog config` on [`dart_tui`](https://pub.dev/packages/dart_tui) (Elm-style Model–Update–View; its `Program` owns the terminal, raw mode, key decoding and rendering): the `Navigator` model is a stack of `Screen`s (file I/O runs as commands through `Navigator.task`), widgets over its components — `MenuScreen` (`ListModel`), `PromptScreen` (`TextInputModel`), `TextScreen` and the shared `ReviewScreen` (`ViewportModel`), `ConfirmScreen`; pages in `config_app.dart` and `workflow_pages.dart` (over `WorkflowSettings` of the core module `settings`).
- **backlog_api** — DTOs, `BacklogApi` and `ProjectsApi` interfaces, `HttpBacklogApi`, `HttpProjectsApi` (pure Dart, compiles for the web).
- **backlog_server** — shelf: `ProjectHub` (hosted projects, `/api/p/<id>` routing, `/api/projects`) with a `HostedProject` per backlog (`BacklogHost`, the `ChangeSource` of its storage → its WebSocket and dispatcher, `ApiHandler` + `DtoMapper`), `RegistryWatcher` (live registry), middleware (token, client allowlist, CORS), multi-address binding.
- **backlog_app** — features `board`, `item`, `projects` (`ProjectsController` picks the open project; one session per project) and `dispatch` (`DispatchController`: the plan, Start, Stop and actions, shared by the board and the detail through `DispatchScope`), each with `application/` (ChangeNotifier controllers and pure logic: `BoardFilter`, `ColumnArrangement`, `DetailNavigation`; shared design tokens in `shared/tokens.dart`) and `presentation/`; depends only on `ProjectsApi` and `BacklogApi`.

Development: `mise run check` (format check, analysis, all tests), `mise run playground` (demo backlog), `mise run serve`.

## 12. Known limits

- Prototype; formats may still change.
- Overlapping `touches` are judged on one snapshot: two agents running `next` at the same moment can still take two overlapping open items (the lock is per item). `lint` then reports `touches-overlap`.
- The board shows only the tail of an agent's raw log (no parsing of `stream-json` yet, no live streaming).
- Agent processes are watched by polling (`/proc` on Linux, `kill -0` elsewhere); the launcher needs `sh`, `git` and `kill`.
- Claims coordinate agents sharing one filesystem; agents on different machines need a shared backlog folder (or the server).
- The web app has no user accounts; protection is the token plus `--host`/`--allow`.
- Filter state, folded columns and the detail's navigation history are not kept across page reloads.
- `section` and `columns` are the only view properties editable from the app; other view changes, statuses and colours are made in the YAML.
- `backlog config` has no pages for the dispatcher's agent profiles, prompts, actions, pull requests and merging; those are edited key by key with *Edit a value…*.
- The theme switch is not remembered across page reloads.
- The server's item cache (§8) still `stat`s every item file per request; very large backlogs pay for that, and the CLI parses every file on each run.
